# 標高（backend）

## 責務

国土地理院のDEMタイルから標高を取り、道の勾配を出す。取込・派生・経路の集計の3段に
分かれており、**実行時に国土地理院へ問い合わせる経路は持たない**。

**対象ファイル**

| レイヤー | ファイル |
|---|---|
| domain | `attributes.py`（`attributes.py: elevation_profile_sql`。区間の断面の点列を間引くSQLを組み立てる）・`elevation_profile.py`（断面から所要時間の点の間と標高・勾配の要約を出す） |
| infrastructure | `dem_elevation.py`（地点の標高を、取り込んだ標高タイルから製品の優先の順に引く。値の無い点だけを次の製品で引く） |
| batch | `source_adapters/gsi_dem_tile.py`（取込と取得。取得はプロファイルが挙げた製品ごとに全タイルを置き場へ写し、取込は写したタイルを製品ごとに読んでint32へ詰める。取込は配信元を叩かない）・`dem_tile_store.py`（写したタイルの置き場と、その製品に無いことの印）・`source_adapters/raster_wkb.py`（画素の並びをPostGISの`raster`へ包む）・`derive_elevation.py`（派生） |

## 3段に分かれている

```
国土地理院 DEMタイル（PNG、256×256。製品ごと）
   │ source_adapters/gsi_dem_tile.py: 製品ごとにint32へ詰めて、製品×タイル1枚=1行
   ▼
source_features(source='dem')          ← 生データ。取り直さない限り変わらない
   │ derive_elevation.py: 区間を等しい間隔に分けた点で、画素ごとに製品を選んで標高を読み、揺れを間引く
   ▼
edge_elevation（断面の点の標高と位置）
   │ 道路網の配列を作るときに読み、要約（start/end・gain/loss・average・一番急な登りと下り）を出す
   │ （road_network_store.py・domain/elevation_profile.py: profile_summaries）
   ▼
経路の集計（domain/route.py: elevation_gain）
```

間引き方は`domain/attributes.py: elevation_profile_sql`が、要約の出し方は`domain/elevation_profile.py`が持つ。派生バッチは
点ごとの画素を読む関係を渡して実行するだけで、勾配の上限も欠測の扱いもそこには無い。

## 断面の点の拾い方と間引き方

標高を拾う点は、OSMの形状点ではなく、区間を較正値`elevation.profile_step_m`以下の等しい道のりに分けた点である。形状点で引くと、
点の間隔が描き手ごとにばらつき、細かく描いた道ほど標高データの揺らぎを登りとして積む。間隔は標高データの格子（DEM5Aは約5m）に
合わせる——格子より広げると、格子が持つ短い起伏を拾わない。

拾った点は、較正値`elevation.profile_tolerance_m`の閾値で間引いてから残す（`domain/attributes.py: elevation_profile_sql`）。断面
（横が道のり、縦が標高）に Douglas-Peucker をかけ、閾値以下の上下を揺れとして消す。残る点の間の勾配は元の点の間の一番急な
勾配を越えない。閾値を十分に越える短い急坂はその急さのまま残り、高さが閾値の数倍に満たない短い段は前後と一緒になだらかに残ることがある。閾値は配信元が公表する標高の精度（DEM5Aは標準偏差0.3m以内。
https://maps.gsi.go.jp/development/hyokochi.html ）に合わせる。平らな道ほど点が少なくなるので、点の数は拾った点の数より
ずっと少ない。間隔と閾値のどちらを変えても派生を作り直す（`TuningEffect.DERIVE_REBUILD`）。

**一番急な登りと下り**（`steepest_gain_percent`・`steepest_loss_percent`）は、GraphHopper の`SlopeCalculator`の max_slope の式で
残した点から測る（1つ前の2点の標高の平均から今の点までの勾配と、区間の両端の勾配の最大。式と最短の長さは
`domain/elevation_profile.py: profile_summaries`・較正値`elevation.steepest_min_interval_m`）。隣り合う2点だけで測ると、5m おきに拾った断面の
短い間の揺れがそのまま一番急になる。下りは逆向きに走ったときの登りとして、逆の順に並べた点に同じ式を当てる（式は前の点を見るので、並べる向きで値が変わる）。平均（`average_grade`）と違い、区間の中で登って下っても打ち消し合わない。ルートの区間の続く坂の斜度（小窓の「最大」）は、この値ではなく、走行の模型が区間を走ったときに踏み増した点の間から作る
（[経路エンジン](routing-engine.md)）——断面の点の間の勾配のままでは、勢いで越える標高の揺れが「最大」に出る。距離は点の道のりの位置の差で測る（点どうしの直線で測ると、曲がった区間で勾配が大きく出る）。

## 断面の点を残す

断面の点の標高と位置（`elevation_profile_m`・`elevation_profile_along_m`。順方向の並びで、逆向きの行は読む側が点を逆順にたどって勾配の符号を返す）を
区間の標高の表に残す。間引いた点なので間隔はそろわず、点の間の長さは位置の差で測る。所要時間と体力は
この点の間ごとに求め（[経路エンジン](routing-engine.md)）、獲得標高・平均勾配・一番急な所の要約も同じ点の間から出す——
目的ごとに別の束ね方で持つと、読む所によって値が食い違う。点の間を勾配として数えるかも両方で同じにする。ルート生成と地図のレンズが
読む要約は、道路網の配列を作るときに断面から出し（`domain/elevation_profile.py: profile_summaries`。判定は所要時間と同じ
`domain/elevation_profile.py: interval_grade`）、勾配と登りの量の材料もここで出す（材料の出どころが`profile`）。派生の表は
要約を持たない——持つと、同じ規則をSQLとnumpyの2つに書くことになる。
道路網の配列は、向きつきの行ごとの始まりの位置と点の数と、全行をつないだ標高と点の位置（区間の長さに対する割合）の配列で持ち、
所要時間と体力を解く点の間（`domain/elevation_profile.py: ProfileSpans`）も、配列を作るときに全区間について1回だけ作って持つ
（`domain/road_network.py: RoadNetwork.elevation_spans`）。
長さ0の区間は、点を等しい間隔に置いて読む（`domain/elevation_profile.py: along_fractions`）。標高の無い点の間と
点が2つ未満の区間は、道路網全体の点の間の勾配の分布どおりの坂として走る（`domain/elevation_profile.py`）。

## 勾配を出さない区間

平均勾配（`average_grade`）が無いのは、標高を出せなかった区間だけではない。勾配として数える点の間が1つも無い区間も持たない。
**舗装公道としてありえない急勾配**（較正値`elevation.max_plausible_grade_percent`。道路網の配列を作るときに読み、作った一様な坂には当てない）の点の間は、
計算したうえで**数えない**と決めた間である。道の起伏ではなくDEMの読み違いで、丸めても上限で切っても直らない。

両端の標高（start/end）は残す。0次ハードフィルタは値の無い区間を
除外しない（`domain/hard_filters.py`）ため、誤った値で黙って経路から外すより安全側になる。

## 橋・高架・トンネル

DEMが返すのは地表面の標高で、桁や坑道の高さではない——谷を渡る橋なら谷底の起伏を、山を
抜けるトンネルなら山の起伏を、そのまま道の勾配として受け取る。**測り間違いではなく別のものを
測っている**ため、値の側では直せない。そこで橋・トンネルの区間は、道が地面と接する両端の
標高だけで上り下りと勾配を出す（派生が断面の点を両端の2点だけにする。`batch/derive_elevation.py`）。

**橋・トンネルの端の頂点は、道に沿って近い地面の標高で直す**（GraphHopper の`BridgeTunnelTowerCorrection`と同じ手順。
式と長さは`batch/derive_elevation.py`の冒頭と較正値`elevation.structure_ground_search_m`・`elevation.structure_slope_floor`）。配信元はDEMから
構造物を除いているので、OSM の橋の端がその除かれた範囲に入ると、端の点は水面や谷底を返す（例: 荒川の朝霞水門の端が2.7m・
堤防の上は約13m）。トンネルの坑口は山肌の高い値を返す。両端だけを引く作りではその値がそのまま構造物の高さになり、端を共有する
隣の道にも急な偽の坂ができる。そこで端の頂点から構造物でない道だけを較正値`elevation.structure_ground_search_m`（初めの値は50m）までたどり、地面の値を
道のりで重みづけて平均した値に置き換える。置き換えで接する道の勾配が急になるものは直さず、直した端に続く道は端から同じ長さ以内を
直線に引き直す（段を残さない）。途中の頂点で区間が分かれた橋・トンネルの内側の頂点は、外へつながる頂点から補う（GraphHopper の
`EdgeElevationInterpolator`と同じ式）。
同じ頂点を端に持つ区間（構造物と、続く道）は同じ値を採る。

橋・トンネルとみなす道は、地図の「橋・高架」「トンネル」（材料`bridge`・`has_tunnel`）と同じで、
判定は`domain/material_sql.py`の`IS_BRIDGE_SQL`・`IS_TUNNEL_SQL`の1か所にある。道が地面から
浮いているか地中にある値だけで、建物の下の通路・道の下の水路・水面すれすれの低い橋のように
道が地表を通る値は、地表の起伏をそのまま勾配に数える。

## 欠測点の扱い

標高が読めなかった点に接する点の間は数えない。**値のある点だけを並べて隣り合う2点でも、元の点列では間に
欠損点を挟んでいることがある**——そのまま隣接扱いすると、欠損区間の実際の起伏が均された
差として混入する。両端の標高は、値のある最初と最後の点。

その製品の整備区域外のタイルは配信元が404を返す。取得は製品ごとに印を置き、取込はその
製品のタイルを行として作らない。どの製品の行も無い地点に落ちる区間は標高を持たない。
取込は、印も本文も無い（まだ試していない）タイルを製品ごとに数えてWARNINGで出す。

タイルの中の欠測（`"e"`）は画素ごとに扱う。上位の製品が欠けた画素だけが下位の製品で埋まり、
どの製品にも値が無い画素は欠測のまま残る。水部がその典型で、配信元は「地図上で水部になって
いる地域では、標高値がデータに入っていない場合や、正確な値が入っていない場合があります」
（https://maps.gsi.go.jp/development/hyokochi.html ）と書いている——下位の製品を足しても、
欠測の大半は埋まらない。

## 向きと標高

区間は向きを持たない1行で、標高も順方向の値だけを持つ。逆向きは読み出し時に導く
（始点↔終点、上り↔下り、平均勾配は符号反転）。地形の
物理量は進行方向に依存しないため、この変換は厳密に正しい。変換はSQLが行う
（`material_joins.py: material_from_clause`）ので、材料の式も評価も向きを
知らない。

勾配の材料（`gradient_percent`）は区間の平均で、どれだけ急かを表し、区間をまたいで足せない。登った量は、獲得標高を
区間の長さで割った足せる材料（`elevation_gain_m_per_km`）として別に持つ。足せるので密度の軸の項にでき、区間をどこで
切っても経路で登った量の和は変わらない。上の入れ替えにより、逆向きの区間ではその区間の下りの量が値になる。

## 経路の集計（`domain/route.py: elevation_gain`）

区間ごとの登りの値から、獲得標高を組み立てる（エンジンと道の窓が呼ぶ domain の関数で、
ファイルは[ルート生成エンジン](routing-engine.md)の対象）。経路の区間の値は探索フェーズで読んだ
材料がそのまま持っているため、ここでDBへ問い合わせ直さない。道の窓は押した区間の登りをこれで足す。値が1つも無ければNone
（0mと「標高が取れなかった」を分ける）。

## タイルの読み方（`batch/source_adapters/gsi_dem_tile.py`）

画素の詰め方を持つ。配信元のパスは`infrastructure/gsi_dem_png.py: gsi_dem_png_path`、製品の順と配信元が公表する最大ズームは
`domain/gsi_tiles.py`が持ち、地図の陰影も同じものを読む。どの製品を取るかは`source_profile.yaml`が持ち、ズームが配信元の最大と
違えば取込の前に止まる（`batch/source_adapters/gsi_dem_tile.py: DemGrid`）。

タイルはPNG形式（256×256。画素の色に0.01m単位の標高を符号化し、欠測は決め打ちの色）で、取込は
画素を標高へ戻し、int32（0.01m単位）へ詰めてPostGISの`raster`（`rast`列）へ入れる。画素の読み方は
`infrastructure/gsi_dem_png.py: read_gsi_dem_png`が持ち、地図の陰影のタイルの変換と共有する。配信元のテキスト形式は更新が
止まっているので取らない（https://maps.gsi.go.jp/development/ichiran.html の備考）。位置・画素の大きさ・型・
欠測値は`raster`の値自身が持ち、`raster`が持てない尺度と、画素の番地を出すのに要る幅だけを
`attrs`へ書く（`raster`から幅を読むと、そのたびに画素が実体化される）。

取込の記録（`source_runs.origin`の`tiles_last_modified`）には、読んだタイルの配信元での最終更新のうち一番新しいものを残す。
取得がタイルのファイルの更新時刻を配信元の`Last-Modified`にして置き、取込はそれを読む。配信元は標高の製品の更新を
タイルの単位で一覧にしておらず（タイルの目録`mokuroku.csv.gz`も標高の製品には無い）、手元が配信元より古いかは、
この時刻と配信元のタイルの`Last-Modified`を比べて言う。

### 製品ごとの性質（配信元の仕様、コードからは導けない）

`PRODUCT_PRIORITY`（`domain/gsi_tiles.py`。地図の陰影・走った記録の標高も同じ順で画素を埋める）は、配信元が「その地点で最も計測精度の良い値」を
採るときの順（DEM5A→DEM5B→DEM5C→DEM10B）である。配信元はこの順を**画素ごと**に当てる
（https://maps.gsi.go.jp/development/hyokochi.html ）ので、派生も画素ごとに当てる——タイル
単位で1製品を選ぶと、選んだ製品の欠測画素が、他の製品に値があっても埋まらない。取得は
この順を使わず、宣言した製品を全部取る。

**製品ごとに最大ズームが違う**（例: DEM10Bはz14まで。同じページに公表）。
各製品をその最大ズームで取り、派生はその製品のズームで頂点の番地を出す。DEM10Bをz15で
求めると、配信元は全タイルで404を返す。

**DEM1A（1mメッシュ、z17）は取らない。** 標高を拾う間隔（上の「断面の点の拾い方と間引き方」）は5m格子に合わせており、
1m格子にしても拾う点が増えない。効くのは間隔を5m未満へ細かくしたときで、タイル数はz15の16倍になる。

**`dem`（サフィックス無し）はDEM5A/5B/5Cを統合したものではない。** DEM10B相当の別データ
セットで、同じタイルでも`dem5a`と違う値を返す。`dem5a`/`dem5b`/`dem5c`はそれぞれ独立に
クエリできる。製品ごとの整備範囲・精度・最大ズームは配信元が公表している
（https://maps.gsi.go.jp/development/hyokochi.html ）。
