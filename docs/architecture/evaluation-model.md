# 評価モデルの層構造（概観）

「この道は走りやすいか」を数字にするまでの段。**実装粒度はここには無い**——材料の解決から
合成コストまでは[評価・スコアリング](../modules/backend/evaluation-scoring.md)、軸の定義と
評価式は[軸スタジオ・評価軸定義](../modules/backend/axis-studio.md)が持つ。

非技術者向けの説明は[README.md「道の走りやすさをどう決めているか」](../../README.md#道の走りやすさをどう決めているか)。

## 4つの段

```
0次: ハード制約   そもそも探索グラフへ入れるか（スコアに一切登場しない）
      ↓
1次: 材料         道路そのものの正規化された値（路面・車線数・停止要因の密度・勾配・風…）
      ↓
2次: 評価軸       材料を束ねて 0〜100 の difficulty にする単位。軸スタジオが管理する
      ↓
3次: 合成コスト   公開軸を利用者の重みで合成し、所要時間へ割増として掛ける（密度の軸は回数に比例して足す）
```

**この4段はそれぞれ変える人が違う。** 0次と1次は「事実をどう取るか」でコードが決め、
2次（軸の形）は管理者が軸スタジオで決め、**重みだけが利用者のもの**である。

## 段ごとの性格

- **0次は0/1で、重みを持たない。** 該当した道路は探索グラフに入らず、コストも
  difficultyも持たない。「通行できない」と「走りにくい」を混ぜないための分離で、
  後者は必ず2次以降で表す。
- **1次は正規化された生データに限る。** 人間が読むための分類ラベル（「自転車レーンあり」
  のような優先順位付きの多値）は材料にしない。分類の順位付けが軸の重み付けと二重になる。
  値の出どころは材料ごとに違う: DBが道路の属性から求める値（大半）、リクエストの条件から都度求める値
  （風。走行方位・出発時刻・想定速度で変わる）、外部の観測を道ごとに引く値（雨。最寄りの雨量計の
  今の観測）。DB以外のものはタイルへ焼けず、ルートを出す前の地図へは専用の配信で届く。ルートの評価へは、
  リクエストの条件で変わるもの（風）は区間の向き・通過の時刻ごとに求め、観測を引くもの（雨）は向きにも時刻にも
  依らないため、探索範囲を組むときにDBの値と同じ列として足す——後者は道の材料と1つの軸で組み合わせられる。
- **2次の軸は単体で評価できる**（[設計原則](design-principles.md)構造仕様11）。軸どうしの依存は、
  非公開の内部軸を公開軸の材料として参照する階層でのみ表す。
- **3次は掛け算である。** 難易度は所要時間への割増として効く。1kmあたりの回数を読む密度の軸だけは、掛けずに
  回数に比例する分を足す（道の切り方で費用が変わらないため）。コスト式と、走行モデルと軸の
  損失の分担・両方を持つ現象の軸の既定重みは[設計原則](design-principles.md)構造仕様13が持つ。

## 地図・探索・ルートで値が違ってよいもの

ルートを出す前の地図の色、探索の費用、ルートの区間の値は、同じ区間・同じ条件なら同じ評価
（`domain/axis_definitions.py: evaluate_axes_array`）から出る。引いた地図の道1本の値も、その道をルートとして走ったときの
ルートの値と同じ決まりで出す（`domain/dynamic_way_values.py: paint_folded_feature_values`）。**違ってよいのは、ルートを
生成するまで決まらない入力に依る値だけ**——地図を出す時点では物理的に決まらず、タイルにも前もって焼けないもの:

- **通過する時刻**（出発からの累計の時間で決まる）: 地図は条件の欄の出発時刻で、ルートは区間ごとの通過予定時刻で出す。
  効くのは時刻を条件に取る材料（例: 風）と、重みが時間帯で変わる軸（軸定義の`time_scope`。例: 夜間）。時間帯の軸は、
  地図では点数をそのまま塗り、ルートでは通過予定時刻がその時間帯に入る区間でだけ重みが効く。
- **進む向き**: 地図は地図の上の向き（走っている間は実際に走る向き）で、ルートは区間を実際に走る向きで出す。効くのは向きを条件に取る材料
  （例: 風・勾配の符号）。
- **想定速度**: 地図もルートも条件の欄の値を使うが、ルートでは通過予定時刻にも効く。

どの軸がどの入力に依るかは、配信のサービスが受け取る条件の型と軸定義の`time_scope`が決め、地図の凡例はそこから
前提（置いた出発時刻・向き）を書く（[地図の色分け](../modules/frontend/map-axis-coloring.md)）。

探索の都合だけで持つ値は、地図にもルートの区間の値にも現れない:

- **欠けた区間の補い**: 重み付きの軸がどれも値を持たない区間は、探索の費用でだけ周りの距離加重平均で補い、
  区間の値は「データなし」のまま返す（[設計原則](design-principles.md)構造仕様10）。
- **前の区間からの曲がり方**（右左折・転回の秒）: 探索の費用と所要時間にだけ足し、軸の値には入らない。
- **迂回率の学習値**: 直線距離から通過予定時刻を見込むための係数で、上の「通過する時刻」の見込みにだけ効く。
  ルートの区間の値は探索がその区間に使った時刻の値を読むので、探索とルートの間では違いを生まない。

## 軸の数も名前もコードに無い

公開軸の一覧・axis_id・既定重みは`axis_definitions`テーブルが持ち、軸の定義ファイルを管理APIへ入れて
増減する。**コード変更もデプロイも伴わない**ため、この文書にも軸の一覧を置かない
（現物は`GET /api/axis-catalog`で引く）。

軸を1つ足すときに通る道は1本だけで、取込の宣言 → 派生 → 材料の値式 → 軸定義、
と進んで frontend には何も足さない（構造仕様3）。

## 得点と生値を両方返す

0〜100の得点は目盛りの引き方に依存する相対評価で、同じ生値でも区間として見るかルート
平均として見るかで意味が変わる。そのため得点の隣に、目盛りに依存しない**生値**（折れ点を
通す前の値）を単位付きで添える。単位が定まらない合成軸は、代わりに材料まで分解した
絶対量を返す。
