# タスクの流れ

## 原則

流れ（タスクの進め方・ゲート・担当・道具・この手順書と流れのスキル）の決まりは、次の原則から導く。各節の先頭の「導く原則」は、
その節の決まりをどの原則から導いたかを示す。

1. **ユーザーの手は、判断と最後の確かめだけ**: ユーザーに求めるのは、何を作るか・どちらの案にするかの判断と、本番での最後の確かめだけ。操作（PC での作業・パッチ当て・本番への書き込み）は求めない。ただし Claude が打てない操作（本番のデータを完全に消す・外部の画面でのアカウント作成等）だけは、打つものを用意して頼む。
2. **回答は、答えられる状態のときだけ**: 問い・答える中身（本番に出ていること）・回答フォームがそろってから、ステータスを回答にする。
3. **状態は1か所・動かす道は1つ**: タスクの状態の正本は1つで、同じ状態を複数の経路で書かない。
4. **詰まりは見ればわかり、あとから判断できる**: どのタスクが止まっていて、何を（誰を）待っているかが、聞かなくても一目でわかる。終わった作業は、あとから判断できる記録（担当の実行の全文・修正前後のキャプチャ・測り直した値）を残す。
5. **守るのは、利用者に見える結果**: テストも見張りも、利用者に見える壊れを先に守る。部品の内側の細部は後。
6. **例外は原則を直して扱う**: 原則に合わない場面が出たら、手順書や流れのスキルに例外を足さず、原則を見直す。原則から導けない決まりは書かない。
7. **issue は約束を持って生まれ、約束が全部果たされたら終わる**: 生きている間は、どの状態にも持ち主が1者いて、持ち主は出力を出して次の持ち主へ渡す。親子に関係なく、issue ごとに自分の約束を持ち、自分の約束が全部果たされたら、ステータスに関係なく終わる（完成）。やめるのはユーザーだけ（見送り）。

## 用語

導く原則: 7。

- **実行**: GitHub Actions のワークフローの実行（workflow run）1回。
- **実行の種類**: 実装担当・検証担当・検査。検査は、Pull Request の CI とマージのコミットの master の CI を含む。
- **実行の status と conclusion**: GitHub の名前と値をそのまま使う。
- **約束**: issue の完了の条件の行。受け入れ条件（ユーザーのもの）と、作る側の完了の定義がある。行に書かれていないもの（マージのコミットの
  検査が通ること等）は約束に数えない。
- **持ち主**: ある状態の issue を、次の状態へ移す責務を持つ者。
- **移管**: 約束の行を、文を変えずに別の issue へ属させ替えること。

## issue のライフサイクル

導く原則: 7・6。

ステータスの値は、次に結果を出す者の行為（実装・検査・検証・回答・保留・待機・完了）。

**生まれる**

| 生まれ方 | 起こす者 | 生まれたときの約束 | 最初の状態 |
|---|---|---|---|
| ユーザーの起票 | ユーザー | ユーザーが書く受け入れ条件 | 実装か待機 |
| Claude の起票（種類が要望） | Claude | Claude が案として書く受け入れ条件 | 回答（採否） |
| Claude の起票（要望以外） | Claude | 完了の条件 | 実装か待機 |
| 切り出し | 実装担当 | 元から移管した行 | 実装か待機（採否は元から継ぐ） |
| 子 | 実装担当 | 親から移管した機能の行 | 実装か待機（採否は親から継ぐ） |
| 対話作業 | 担当か開発機の対話のセッション | 開発機でしかできない作業の結果 | 実装（持ち主は開発機の対話のセッション）。元の issue の前提に張る |

**生きている間**

| 状態 | 持ち主 | 次の状態へ移る条件 |
|---|---|---|
| 実装 | 実装担当（対話作業は開発機の対話のセッション） | Pull Request を出した → 検査／問いを出した → 回答／待つ相手を張った・着手可能日時を入れた → 待機／約束が全部果たされた → 完了 |
| 検査 | 検査 | Pull Request の検査が合格 → 検証、合格でない → 実装／マージのコミットの検査が合格 → 約束の残りしだい、合格でない → 実装 |
| 検証 | 検証担当 | マージした → 検査／下書きへ戻した → 実装／問いを出した → 回答 |
| 回答 | ユーザー | 答えた → 答えに応じた状態 |
| 保留 | ユーザー | 解いた → 事実から決まる状態 |
| 待機 | 待つ相手（前提・子・親・日時） | 相手が閉じた・日時が来た → 事実から決まる状態 |
| 完了 | なし | — |

どの状態でも、約束が全部果たされたら完了へ移る（下の「終わる」）。

**実行の終わり**: 担当の実行は、状態か約束のどちらかが動いていれば正当に終わる。約束が動いたとは、行にチェックが付いたか、移管が
あったこと。どちらも動かずに終われば、イレギュラーとしてユーザーに渡す。

**終わる**: issue ごとに、自分の約束が全部果たされたら、どの時点でも完成で終わる（Pull Request・前提・子・担当の実行・マージのコミットの
検査に関係なく。動いている担当の実行は取り消す）。待つのは、ユーザーが置いた保留と、Claude がまだ読んでいないユーザーの文だけ。
ユーザーの見送りは約束ごと終わる。親が閉じれば（見送りか、ユーザーが完成で閉じた）、開いた子は見送りで終わる。

## 流れのあらまし

導く原則: 3・7。

タスクは GitHub の issue で、大きすぎるものは、要望ごとに切り出すか、1つの要望を機能ごとに子（sub-issue）へ分ける（.claude/skills/file-issue/SKILL.md「分ける」）。
ステータスは issue の欄（issue fields）「ステータス」に置き、**ゲート（`tools/flow-gate/`）が事実から1つの決め方で決める**（`tools/flow-gate/src/decide.js: decide`）。
事実は、issue（開き閉じと閉じた人・完了の条件・問いと答え・前提・着手可能日時・ラベル・時系列）・作業ブランチの Pull Request（下書きか・差し戻し・master とぶつかっているか）と、
その先頭のコミットとマージのコミットの検査の実行・担当の実行と終わりのコメント。同じ事実からは何度決めても同じで、ゲートは今の値と違う所だけを書く。
Claude はステータスを書かない。それぞれの状態で何をするかは、この文書と流れのスキル（`.claude/skills/` の task-work・ask・file-issue・dev-session）が決める。

## 置き場と役割

導く原則: 1・3。

| 置き場・役 | 持つもの・すること |
|---|---|
| 置き場のリポジトリ（`flow.config.json: tasks`） | タスクの issue・問いと答え・記録（記録は issue にだけ持ち、git に写さない）。ステータス・実行の status・優先度・規模・着手可能日時は組織の issue fields（`flow.config.json: fields`）で issue が持つ。どう見せるか（Project のボード・ビュー・issue の一覧の絞り込み）は GitHub の画面で決め、ゲートは関わらない。種類「対話作業」（`flow.config.json: dialogType`）は、開発機の対話のセッションだけが進めるタスク |
| ゲート（Cloudflare の Worker。Webhook を受ける `ridecompass-gate` と、Access の内側の回答フォーム `ride-compass-answer`） | 出来事と定時に事実を読み、ステータス・欄「実行の status」・担当者・本文の先頭のボタン・問いのラベル・種類を書き、孫を外す。決めたステータスを作業ブランチの Pull Request へ写す（検証で下書きをレビュー可能にし、見送りで閉じる・閉じた issue の Pull Request を閉じる。親が閉じて見送りで閉じる子も同じ）。issue の情報は持たない（事実の持ち主は GitHub）。持つのは、出来事の受け箱と、失効の時刻まで変わらないインストールの鍵だけ。見回りが担当を振り出す。回答フォーム |
| Claude（hidakagit-bot の名義） | 作業・問いとコメント・分けることと前提・確かめとマージ・欄の規模と優先度と着手可能日時・開発機で作業中のラベル |
| ユーザー（hidakagit） | 判断（回答フォームか、開発機の対話のセッションのチャット）・本番での最後の確かめ・保留と完了・ラベル（`急ぎ` 等） |

ゲートは自分の書き込み（送り主 `flow.config.json: gateBot`）を無視する。種類は作るとき（最初に付いた種類）に決まり、
対話作業の境目をまたいで変えるとゲートが戻す。

## ステータスと割り当て

導く原則: 1・2・3・4・7。

決め方の正本は `tools/flow-gate/src/decide.js: decide` で、ここには読み方を書く。

- **保留と完了だけは、ユーザーの決定も受ける**（ステータスの欄を変える・閉じる・問いへの答え・チャットの答えの記録）。保留は、ユーザーが置いたら出すまで保つ
  （持っている担当の実行は取り消す）。完了は、完成（完了の条件が全部済んだ）か見送り（Close as not planned）でだけ受け、条件が残ったまま完成で
  閉じる・完了へ動かすと、ゲートが事実へ戻す。ほかのステータスは事実から決まり、ユーザーが動かしてもゲートが事実へ戻す。
  Claude は保留と完了を自分の判断で書かない（止める・終えるのはユーザーの決定。原則1）。
- **誰の番か（2階）**: ゲートの決め方は2階で、1階が成果物の事実と関係性からステータスを決め、2階がその結果だけを読んで持ち主（次に結果を
  出す者）を1つの決め方で決め、担当者と振り出しをそこから導く（`tools/flow-gate/src/decide.js: dispatchKind`）。持ち主は、ユーザーに問わないと
  進めないもの（回答・保留）はユーザー、検査・待機は事実が動くのを待つ Claude、実装・検証は、対話作業とラベル「開発機で作業中」
  （`flow.config.json: devLabel`）のある issue なら開発機の対話のセッション（ラベルが無い間はユーザー）、ほかは担当、完了は無し。担当者は2択で、持ち主がユーザーなら
  ユーザー、ほかは Claude（hidakagit-bot）、完了は無し（手で変えても、その出来事でゲートが戻す）。ステータスは対話作業でも事実どおり（検査の間は検査）。
- **待機**: 次に結果を出すのが担当（実装・検証）でも、待つ相手（前提・子が開いている・着手可能日時が先・親が保留か閉じた）がある間は待機。
  待つ相手は、約束が残っている間に問う・振り出す時機を待つためのもので、完了は止めない（上の「終わる」）。子は親の要望を機能ごとに分けた
  部分なので、開いた子がある間は親の確かめを問わない。見送りか重複で閉じた相手があれば、続けるかを一度だけ問う（種類「続行」の問い。ゲートは事実を見つけて問うだけで、決めるのはユーザー）。見回りは待機を振り出さない。
  前提の対話作業は開発機の対話のセッションしか進めず、果たし忘れると黙って待ち続けるので、`flow.config.json: dialogIdleHours` より長く動いていなければ、待っているタスクにユーザーへの知らせを出す（同じ知らせは重ねない）。
- **欄「実行の status」**: ステータスが指す種類の、動いている実行の status を GitHub の値のまま写す（無ければ空。表示のためだけで、決め方には使わない）。
  検査は、検査の実行のうち終わりから最も遠い status（必須の検査が1本になるまでの暫定。tasks#810）。
- **作業の上限**: 担当の1回の作業は3時間まで（`claude-task.yml` の `timeout-minutes`。ジョブが始まってからの正味の時間）。超えると GitHub が実行を取り消し、
  状態も約束も動かさずに手放したことになって、ゲートがイレギュラーを問う。ゲートは時間を測らない。順番待ちの長さは、欄「実行の status」の queued で見える。
- **入口**: Claude が起こした要望は、何を作るかがユーザーの判断なので、ゲートが採否を一度問う（採否の問いがあるかは、issue のコメントで見る）。
  子と、本文に「分割元: #<元>」のある切り出しは、採否を親か元から受け継ぐ。
- **子**: 子（親を持つ issue）は、優先度・着手可能日時・「急ぎ」・保留を自分の欄でなく親の値で見る。約束（完了の条件）は自分の本文に持ち（原則7）、
  ほかの issue と同じく、自分の約束が全部果たされたら完了。親が開き直されない閉じ方で閉じたら、開いた子を見送りで閉じる。
  孫は張られた直後に外して知らせる。
- **持たれている間**: 担当の実行（順番待ちを含む）がある間は、その担当の種類（実装か検証）。
- **ユーザーが書いた文**: 答えのコメントの欄の文とコメントは、ゲートが中身を読まず、Claude が読むまで Claude の番にする
  （閉じたあとの文なら開き直す。閉じるときに一緒に書いた文は閉じる決定の一部）。担当は、終わりのコメントの「読み始め」より前の文を読んでいる。対話作業とラベル「開発機で作業中」の issue は、開発機の対話のセッションが読んでから書くので、
  Claude のコメントより前の文を読んでいる。
  保留の間は、保留から出たときに読む。
- **問い**: 最新の「## 問い」に答えが無ければ回答。読めない問い（.claude/skills/ask/SKILL.md「問い」の読める前提に外れたもの）も答えを待ち、回答フォームは
  読めない理由を出して、回答内容を出さずに書く欄と次遷移で答えを受ける。答えの無い問いが残っていても、約束が全部果たされたら完成で閉じる（上の「終わる」）。ゲートが出した問い（ラベルの形の「出す者」がゲートのもの）は、同じ事実から決め直して同じ問いが出る間だけ読み（一度問うたこと・担当の実行・保留・読まれていない文は、問いを出す事実に数えない）、出なくなったら読まずに下の決め方で決める。担当が出した問いは、ゲートが中身を読まないので答えまで読む。担当の終わりのコメントは、そのあとに答えがあれば答えで扱ったものとして、終わり方を判じ直さない。
  答えの決定は、答えの「次遷移:」の行（続ける・保留・見送り）だけで決まり、回答内容（選んだ案・済ませることの値・コメント）は遷移先が読み、ゲートは
  読まない（確かめることの値は、回答フォームが本文の約束へユーザーの名義で書く）。見送りなら見送りで閉じ、保留なら保留、続けるなら遷移先の Claude が答えを
  読むまで実装（約束が全部果たされていれば完成で閉じる）で、読んだあとは下の決め方へ進む。書いた文のある答えは、Claude が読んだあとに当て、当てたことを一度だけ知らせる。答えのあとにユーザーがステータスを変えたか開き直したら
  （issue の時系列の事実）、その答えは当てない。ゲートが出す確かめの問いの確かめることには、ユーザーが確かめる条件ごとに、条件の文と行の下の「見る所と要点」が並ぶ
  （無い条件は「書かれていません」と出る）。答えの無い問いがある間（本文の先頭に回答のボタンがある間）は、ゲートがラベル「問い: <ラベル>」を付け、
  答えが当たるか問いが要らなくなったら外す（一覧で、誰に何を問うているかが見える）。
- **手放したあと**: 作業ブランチの開いた Pull Request は、検証担当が下書きへ戻したか、master とぶつかっている（GitHub の計算中は数えない）なら
  実装（取り込むのは実装担当で、検証担当を起こしてもマージの手前で戻すだけになる）、検査が終わるまで検査、合格なら検証（下書きなら
  ゲートがレビュー可能にする）、合格していなければ（不合格か、検査の実行が1本も無い）実装（検査が始まる形で push するのも直すのも実装担当）。
  合格は、GitHub が必須の検査の合格に数えるもの（成功・スキップ・中立）だけで、1本でも終わっていなければ終わっていない。担当のワークフローの
  実行（振り出した時点の master の先頭のコミットに付く）は検査ではないので数えない。変異テストの生き残りはゲートが読まず、検証担当が読んで、扱われていなければ下書きへ戻す。
  Pull Request が無ければ、マージのあとの残りはマージのコミットの検査（デプロイを含む）が終わるまで検査、合格していなければ実装（実装担当が打ち直すか直す）、
  残りが無ければ完成で閉じ、残りが全部ユーザーの確かめなら回答にしてゲートが確かめを問う（本番に出てから問う）。
  担当が手放したとき、次に結果を出すのが手放した担当と同じ種類のまま（状態が動かず）、その実行で約束も動いていなければ、イレギュラーを問う。
  約束が動いたかは、担当の終わりのコメントの「読み始めの完了の条件」と今の本文を比べて決める（チェックが増えたか、消えた行が全部その実行の間にできた
  移管先にある）。
- **残り**: 本文の完了の条件のうちチェックの無いもの（`tools/flow-gate/src/questions.js: remaining`）。完成は、残りが無くなった事実で
  決まり、ユーザーが基準になる確かめは、その答えが行を満たす。
- **受け入れない書き込み**: 読めない問い（回答内容を無いものとして答えを受ける）・印の間の見知らぬ行・形の合わない着手可能日時は受け入れず（読めない
  着手可能日時はまだ先と読む）、ゲートが1つのコメントで読めない理由を知らせる（`tools/flow-gate/src/decide.js: decide`）。書き方はスキルが持ち、
  守られなかったときをゲートが捉える。
- **本文の先頭**: 回答の間だけ、ゲートが回答フォームへのボタンを置く（区切りの注 `<!-- flow-gate -->` の間）。GitHub の画面では本文の下の欄まで
  毎回たどるのが負荷になるので、本文の先頭に置く（ユーザーの決定）。
- **読む値の鮮度と要求の数**: ゲートは、変わりうる値（issue・Pull Request・検査・実行の一覧・開いた issue の一覧）を出来事1件の処理の中でだけ使い、
  次の出来事では読み直す。1件の決め直しは、事実を読む1回と、本文・欄・担当者・ラベル・種類・コメント・Pull Request の操作・閉じるをまとめた
  書き込み1回（GitHub は1回の要求に並べた書き込みを並べた順に行う）と、取り消す実行ごとに1回（Actions の取り消しには1回にまとめる口が無い）。
  当て直すと結果が変わる答え（保留・見送り）があるときは答えより後の時系列を、担当が約束の行を消して終えたときは移管先の候補を、それぞれ1回読み足す。
  定時は、担当の実行の一覧と開いた issue の一覧を1回ずつ読み、振り出しと決め直す番号の列挙の両方に使う。

**1つのタスクを触るのは1者だけ**: 担当は振り出しでだけ起き、同じ issue の実行は担当のワークフローの `concurrency`（`queue: max`）で1本ずつ順に動く。
担当が付いているかは、GitHub の担当のワークフローの実行の一覧（`tools/flow-gate/src/facts.js: recentRuns`。終わっていない実行）から、決め直すたびに読む。

## 様子を見る

導く原則: 4。

issue の欄と担当者そのものが様子で、ステータスは事実から決まるので実態になる（あなたの番は担当者 hidakagit で絞る）。動いている担当は Actions の画面（Claude Task の「#<番号> <種類>」）。

GitHub の失敗の知らせが届く。この症状で拾えない詰まりは、例外を書き足さず流れの摩擦として記録する。

## コミット

導く原則: 4・3。

**1タスク=1コミット**（子は子ごと）。コミット履歴は、件名と本文だけでどこまで戻せばよいかを特定できる状態に保つ。問い・決定・確認の結果は

  しか選べず（公式の文書 `gh help environment`）、権限の拒否の規則は先頭の変数の代入を越えて当たるので、付けた打ち方と
  付け忘れた打ち方を見分けられない（公式の文書「Configure permissions」の Wrappers）。

- **記録**: Actions の実行の記録に、「#<番号> <種類>」の名前で並ぶ。コードのリポジトリは公開なので、記録は誰でも読める。
  担当の出力の全文と報告は記録に出さない（出るのは指示文と、手数・費用の目安）。担当の最後の発言は、非公開の置き場の issue にだけ書く（4）。
  手番の記録（担当が何をどの順でしたか）は、非公開の置き場のリリース「担当の手番の記録 <日付>」の添付に残り、終わりのコメントの
  「後始末がしたこと」にそのリンクが出る（4）。開けるのは置き場を読める人だけで、置き場の Releases から消すまで残る。

- **開発機が要る**: 開発機にしか無いもの（本番への調べ `run_probe.py` の SSH の鍵・開発 DB の実データ）が要るタスクは、Actions では
  進めない。担当は、それが要ると分かったところで作業を止め（途中の変更は作業ブランチへ push してから）、issue にラベル
  「開発機が要る」（`coordinator.devLabel`）を付け、何がなぜ要るかをコメントに書いて終える。ユーザーが最初から付けてもよい。
  振り出しはこのラベルの付いたタスクを飛ばし、ユーザーが開発機の対話のセッションで扱う（「開発機の対話のセッション」）。

**作る担当**・**確かめる担当**のどちらも、作業は担当のワークフローが取り出した作業ツリーの中だけで行う。どの終わり方でも
（PR を出した・問うた・段階に分けた・完成で閉じた・確かめてマージした／閉じた・開発機が要ると返した）、手順の中で当たった改善点を
「改善を起票する」のとおり起票し、範囲の外の気づきに行き先か直さない理由を付け（下の「範囲の外の気づき」）、push と issue への
報告をして終える。次の担当を起こすのは振り出しなので、担当は触れない。

**範囲の外の気づき**: 作業の中で見つけた、今のタスクの範囲の外のもの（流れの改善点に限らず、製品のコード・文書・テストの誤りや
残骸も。[fixing.md](../../.claude/rules/fixing.md)「人が見るしかないもの」の2）は、報告に書くだけで終えない——閉じた issue のコメントは読み返されず、
次の回に届かない。1件ずつ、次のどれかをしてから終える。今の差分で直せるものは直す（「改善を起票する」）。

1. 寄せる: 直す場所が同じ開いた issue（探し方は「前後関係と組」の「探す」）があれば、そこへコメントで書く（「改善を起票する」の「重ねない」）。
   書いたあと、寄せ先がまだ開いていることを `GH_TOKEN=$FLOW_BOT_TOKEN gh issue view <番号> -R ridecompass/ride-compass-tasks --json state` で見る（探してから書くまでに
   閉じると、コメントは誰にも読まれない）。閉じていれば 2 へ。

2. 起こす: 無ければ、「改善を起票する」の「書き方」のとおり起票する（種類は気づきの性質で選ぶ）。

**作る担当・確かめる担当の終え方**: 手番を終える最後の発言は、その回にやったことの要約にする（後始末が終わりのコメントへ写す。
「担当のワークフローの1回」の4）。終わり方（PR を出した・問うた等）と、やったこと・作ったもの・書いたもの（Pull Request・コミット・
問い・起票やコメントを足した issue）を番号かコミットの ID で名指し、読み手がそれを開いて確かめられるように書く。詳しい中身は
Pull Request・問い・issue に書き、最後の発言へ写さない。

2. backend と frontend の依存とテスト用の DB は、担当のワークフローが入れてある（backend は `python`、frontend は `frontend/node_modules` と Playwright の Chromium）。
   入れたのは master の版の依存のファイルからなので、1 のあと `git diff --name-only origin/master -- backend/requirements*.txt frontend/package-lock.json`
   で作業ブランチとの違いを見る。backend のファイルが出たら `python -m pip install -q -r backend/requirements-batch.txt -r backend/requirements-dev.txt`、
   `frontend/package-lock.json` が出たら `npm ci --prefix frontend` と `npx --prefix frontend playwright install chromium` で入れ直す（Chromium は
   `@playwright/test` の版ごとに別のものが要る。作業の途中で依存のファイルを変えたときも同じ）。

- 作る前に、自分の直す場所で開いた issue を探し、前後関係と組を張る。探した鍵は報告に書く（「前後関係と組」の「探す」）。

- 直す範囲を母集団で決めるタスクは、作る前に本文の母集団の検算（[fixing.md](../../.claude/rules/fixing.md)「範囲は性質から導く」の4つの欄）を
  今の版で当て直す（起票の版から動いた所がある）。欄が欠けていれば自分で書く。検算の例を道具が拾わなければ、道具を広げるか
  拾わない形に足し、経緯に書く。完了の条件が母集団を決めた道具の0件だけなら、同じ節の「検証は別の入力で行う」の行を足す。

- 完了の条件（マージのあとの残りも）に、開発機にしか無いもの（「担当」の「開発機が要る」）でしか確かめられない行があれば、
  同じことをテスト DB・CI で確かめる形（前後の SQL 文の比べ・テストの期待値等）へ書き換え、経緯に書き換えた理由を書いて進める。
  書き換えると確かめる対象か範囲が狭まるなら書き換えず、「開発機が要る」のとおりラベルを付けて返す。

- 1つの Pull Request に収まらないと分かったら、「段階に分ける」のとおりに分けて終える（段階は次の起動から1件ずつ振り出される）。

- 依存の版上げを取り込むタスクは、同じ版を出している dependabot の Pull Request を issue の本文に番号で名指し、完了の条件に
  「dependabot の #<番号> が閉じている」を書く（判定役は issue が名指した dependabot の Pull Request だけを、担当が閉じてよいものと読む）。
  閉じるのは作る担当で、マージのあとの残りとして済ませる（下）。dependabot は master が同じ版になっても閉じないことがあり、
  閉じる条件は公式の文書に無いので、閉じるのを待たない。`gh pr view <番号> -R hidakagit/ride-compass --json state` が `OPEN` なら
  `gh pr close <番号> -R hidakagit/ride-compass --comment "<取り込んだ Pull Request> で同じ版を取り込んだ"` で閉じ、閉じたかを
  確かめる担当の4と同じく `state` で見る。

- マージ済みの Pull Request があって戻ってきたタスク（マージのあとの残り）は、残りを済ませて完了の条件にチェックを付ける。
  確かめの行だけが残っていれば、確かめてほしいことを問う（完成・進める等は回答フォームが一律に出す）。
  残りが時間を待つものだけ（数時間後・翌日の観測、外部の公開の日など）で、今は済ませられないなら、待たずに着手可能日を
  入れて終える（`field.js <番号> 着手可能日 <YYYY-MM-DD>`）。日は、済ませられるようになる時刻を日本時間の日付へ切り上げる（欄は日付だけで時刻を
  持たないため、数時間の待ちでも最長1日遅れる）。issue へのコメントに、何をその日に済ませるかを書く。PR も問いも出さずに終えてよく、
  後始末が未着手へ戻す。その日に振り出された担当は、残りを済ませたら欄を消す（`field.js <番号> 着手可能日 消す`）。
  本番の実物（画面・API）で確かめてほしいときは、本番にマージの版が出るのを待たずに問い、判断材料に、ユーザーが自分で版を
  見分ける方法を必ず書く（出る前に見ると、ユーザーが前の版を見て「直っていない」と答える）。master の CI（e2e とデプロイ）を
  待たないのは、待ちが確かめの作業より長くなるためで、版を見分けるのはユーザーが答えるときに任せる。問う前に、本番に
  出たかを1度だけ見る。見る口は変更が届く側で決まる: frontend は `/api/version`、backend は `/health` の `commit`
  （宛先は docs/architecture/tech-stack.md「本番の宛先」。backend は、Pull Request の差分に `scripts/deploy_gate.py: deploy_paths`
  が導くファイルがあるときだけ見る）。`git merge-base --is-ancestor <マージのコミット> <本番の commit>` が 0 で終われば出ている
  （本番の commit が手元に無ければ先に `git fetch origin`）。
  変更が frontend に届くなら、出ていてもいなくても、判断材料の先頭に画面での見分け方を書く: 「画面右上のメニュー（︙）の
  『バージョン表示』の版が <8文字> なら修正を含む版。違えば下の見分け方で見る」。8文字は、出ていれば見た時点の本番の `commit`、
  出ていなければマージのコミットの頭8文字（窓は版の8文字だけを出し、前後を持たないので、違ったときは窓では見分けられない）。
  backend にだけ届く変更は、窓に出ないので下の見分け方だけを書く。

- 出ていれば、開く URL と見た時点の `started_at` を書き、「`started_at` がこの時刻以降なら修正を含む版」とする。

- 出ていなければ、master の CI の一覧（`https://github.com/hidakagit/ride-compass/actions/workflows/ci.yml?query=branch%3Amaster`）と
  マージのコミットの件名（Pull Request の題名。一覧の実行の名前になる）を書き、「この名前の実行か、それより上に並ぶ（後の）実行が
  成功で終わっていれば修正を含む版。どれも実行中なら終わってから見る。失敗か取り消しで終わっていれば、確かめずに次のステータスを
  未着手にして、補足にそう書く」とする（CI の `deploy-frontend`・`deploy-backend` は、出したコミットが本番の `commit` になるまで
  待って終わる）。`commit` が見た時点の値から変わったかでは見分けない（master の CI は1本ずつ順に走るので、マージより前の
  コミットの実行が後から出し、修正を含まない版に変わることがある。`ci.yml` の `concurrency`）。

補足に実行が失敗か取り消しで終わったと書いた答えは、確かめが済んだとは読まず（下の「確かめの問い」の答えに当てない）、
今の本番を同じく見て（出ていなければ master の先頭の CI を見て、出ない理由を判断材料に足して）、同じ形で問い直す。

- コードを変えないタスク（調査・見積もり・計測）は、結果を本文に書いて自分の分の完了の条件にチェックを付け、結果を確かめてほしいと
  問う（Pull Request が無いので、完了はユーザーの答えで決まる）。

5. コードのリポジトリに Pull Request を出す（`gh pr create --base master --head orch/tasks-<番号>`。
   コードのリポジトリは hidakagit のものなので、hidakagit の名義で打つ。担当は gh の既定（`GH_TOKEN`）が `CODE_TOKEN`
   （「担当」の「名義」）、開発機の対話のセッションは gh のログインのままでよい）。
   題名と本文は、そのまま master のコミットになるので、下の「コミット」の書式で書く（題名が件名
   `tasks#<番号>: …`、本文が背景・課題・成果・検証・増減・残り）。書式の中に、次のものを入れる:

- 課題: 約束の差分（足した約束・消した約束・変えた約束を1行ずつ。約束は利用者や運用から見た振る舞いで、issue の要約・
  完了の条件・設計書の決まりの言葉で書く）。約束が増えない変更で実装かテストの行が増えたら、増えた行ごとの理由。
  確かめる担当は差分の足した行をこれに当てる

- 増減: `python scripts/review_checks.py change` の出力の行（出た規模の札は記録で、Project の欄は付け直さない。「規模の札」）

- 0: 取り消しのジョブと、それに `needs` で続くジョブだけを流し直したので、`gh run watch` から待ち直す。

- 1: 直すもの無しの取り消しではないので、「落ちたら」に当てる。

- 3: 3回流し直しても同じ取り消しで終わった。Pull Request を開いたまま、6 の報告に実行の id と道具が出した行を書いて終える
  （タスクは検証中のまま残り、確かめる担当が同じ扱いで続ける）。

- 4: 実行がまだ終わっていないので、`gh run watch` で終わるのを待ってから打ち直す。

**分布の前後**
落ちた絞り込み・二重に数えた値は、エラーにもテストの失敗にもならず、値の偏りとしてだけ現れる。タスクの作業ではこれを測らない
——作る担当も確かめる担当も、差分がどこに触れても（値を変える目的の変更も、値を変えるつもりのない変更も同じ）分布の前後を
測らず、Pull Request の本文に前後の行を求めず、そのために「開発機が要る」にもしない。値の偏りは、本番の派生を作り直すたびに
派生の表の全部の値の列を前と後で測る記録で確かめる（手順は [deployment-sync.md](../../.claude/skills/production-data/SKILL.md)「派生データの作り直し」）。
気づく時点は、Pull Request ではなく本番の作り直しになる。
軸の評価の式（`backend/app/domain/` の軸の評価）だけを変える変更は派生の表を変えず、この記録に出ない。そうした変更が本番に出たら、
出たあとに全部の軸の張り付きを本番で1回測り（`backend` で `python scripts/run_probe.py scripts/measure_axis_saturation.py`。読むだけ）、
出力をそのタスクの issue にコメントで書く。本番を読めるのは開発機なので、開発機の対話のセッションが打つ（「開発機の対話のセッション」）。張り付いた軸が
あれば、その変更を疑う。

- コードのリポジトリは、master に入れる前に必須チェック（`ci.yml` の `ci-ok`・Docs Consistency・Claude Gate の `flow-gate` 等）が Pull Request で通ることを
  求める（ルールセット。管理者にも効く）。最新の master の取り込みは求めない（求めると、1件入るたびにほかの Pull Request が
  全部載せ直しと CI の待ちになり、並べて進めた分が1本ずつに潰れる）。それぞれ通った Pull Request の組み合わせで壊れたものは
  master の CI が捕まえ、通るまで本番へは出ない（`ci.yml` の `deploy-backend`・`deploy-frontend`）。マージは hidakagit のトークンで打つので、
  落ちた知らせは GitHub の通知（Actions の失敗）で hidakagit に届き、直すのは普通のタスクにする。

- 開いた（開き直された） → 進行中なら検証中。ほかの状態なら何もしない

- マージされずに閉じた → 未着手（閉じたときのコメントを作る担当が読んでやり直す）。master と競合して Merge が押せない
  ときも、確かめる人が「競合」と書いて閉じる（競合を知らせる出来事は GitHub に無い）

- マージされた → 残り（チェックの無い完了の条件）が無ければ完了（completed）、あれば残りを書いて未着手（作る担当が残りを済ませる）。
  残りがユーザーの確かめの行だけなら、確かめる担当がマージした同じ回で問いを置いて回答待ちにする（下の 3）。PR の出来事は
  検証中のタスクだけを動かすので、問いとマージのどちらが先に届いても回答待ちのまま

- Pull Request を閉じた・マージしたのに検証中のまま止まったら、先に `gh pr view <番号> -R hidakagit/ride-compass --json state` で
  Pull Request の状態を見る。`OPEN` なら閉じる・マージする操作そのものが通っていないので、打ち直す（確かめる担当の4・5）。
  `CLOSED`・`MERGED` なのにステータスが動かないときだけ、知らせが届かなかったので、コードのリポジトリの Settings →
  Webhooks → Recent Deliveries から Redeliver する（GitHub は届かなかった出来事を送り直さない。3日分まで）。

- Pull Request を開いたのに進行中のまま止まったら、作る担当の実行が終わるときに、後始末が作業ブランチの開いた Pull Request を見て
  検証中へ入れる（「担当」の「担当のワークフローの1回」の4）ので、担当は手で直さない。後始末の無い開発機の対話のセッションが出したときは、
  `move.js <番号> 検証中 <理由>` で入れる。

2. 確かめた結果を、満たしていてもいなくても issue にコメントで書く（見出し「確かめた結果」）。完了の条件の1件ごとに、
   何をどう見て（実行したコマンド・開いた画面）何が出たかを書き、撮った画面は Pull Request へ `attach.js` で貼る
   （貼り方と貼れないときの扱い・添える説明の中の本番の宛先は、作る担当の5と同じ）。
   設計書の条件は、選んだ条件（文書と節）・確かめた方法・出た値を書く。足した行と約束の突き合わせは、どの約束にも
   当たらなかった行があれば、その行と理由を書く。消した・まとめたテストは、数えた本数と表の行の数・選んだ壊れ方（実装のファイルと変えた行）・回した残す側の
   テストのファイル・落ちたテストの名前（通ったなら通ったこと）を書く。約束ごと消した行を選んだなら、選んだ行・打った `git grep` と
   件数（持ち主の中の一部なら、出た行ごとの持ち主）・当たった課題の約束の行を書く。ここに書いたことだけが、確かめた証拠として残る。

3. ユーザーが見るべきだと判断したら（利用者から見える振る舞い・モジュールの設計が変わる等）、完了の条件に確かめてもらう行
   （`- [ ] ユーザーが確かめる: …`）を足し、理由を書く。マージは確認を待たない。
   マージしたあと、残りがユーザーの確かめの行だけなら、同じ回で `ask.js` で問う（作る担当を起こし直さない）。本番の実物で
   確かめてほしいときも、本番に版が出るのを待たず、作る担当の3の「本番の実物」のとおり判断材料に版の見分け方を書いて問う。
   残りが開発機にしか無いもの（「担当」の「開発機が要る」）で確かめる行だけなら、マージの前に issue にラベル「開発機が要る」を
   付ける（付けないと、未着手へ戻ったところで Actions の作る担当へ振り出され、何もできずに返す）。
   **マージで重なりが消えた前提を外す**: マージしたあと残りがあって issue が開いたまま残る（未着手へ戻る・確かめの問いで回答待ちに
   なる）なら、同じ回で、この issue を前提にしている後の issue（`GH_TOKEN=$FLOW_BOT_TOKEN gh issue view <番号> -R ridecompass/ride-compass-tasks --json blocking`）を
   1件ずつ見る。後の issue に書かれた張った理由（無ければ後の本文のやること）を読み、後が依っていた中身がどれもこの Pull Request で
   master に入り、残り（マージのあとの作業・ユーザーの確かめ）に依らないなら、前提を外し（`GH_TOKEN=$FLOW_BOT_TOKEN gh issue edit <後> -R ridecompass/ride-compass-tasks --remove-blocked-by <番号>`）、
   外した理由（依っていた中身と、それが入った Pull Request・残りが何で、後がそれに依らないこと）を後の issue にコメントで書く。
   残りに依るもの（残りの作業が後の材料になる・確かめの結果しだいで後の作業が変わる等）は外さない。外さないと、後は先が残りを
   済ませて閉じるまで振り出されない（「前後関係と組」の「向き」）。外したもの・外さなかったものと理由は、自分の issue にコメントで書く
   （2 の結果はマージの前に書くので、そこへは足さない）。
   **作る担当の着手より後に届いた依頼**: 作る担当は着手したときに issue のコメントを読む（作る担当の3）ので、そのあとに届いた
   依頼（ほかのタスクの担当からの申し送り等）は Pull Request に入っていない。issue のコメントを読み、そうした依頼のうち完了の条件に
   無いものは、本文の完了の条件へチェックの無い行として足し、2 の結果にどのコメントから足したかを書く。足した行は閉じる理由に
   しない（4 の「満たしていない」には当てない）。マージすると残りとして未着手へ戻り、作る担当がマージのあとの残りとして済ませる。

4. 1 で「満たしていない」とした条件のどれかに当たれば、足りないことを書いて Pull Request を閉じる（`gh pr close <番号> --comment <理由>`）。
   閉じる操作は GitHub の API の失敗で通らないことがあるので、閉じたかは `gh pr view <番号> -R hidakagit/ride-compass --json state` で
   `CLOSED` が出るかで見て、`OPEN` のままなら閉じ直す。ゲートが未着手へ戻す。それ以外の気づき（本文の数字の誤り・書き漏れ・使われない import 等）は閉じる理由にせず、2 の結果に書く。
   そのうち Pull Request の範囲の中で master に残るもの（差分が変えたものを書いたまま直し漏れた文書の行・使われない import 等）は、
   3 の「着手より後に届いた依頼」と同じく本文の完了の条件へチェックの無い行として足し、2 の結果に足したことを書く（マージすると
   残りとして未着手へ戻り、作る担当が済ませる）。結果のコメントは閉じた issue に残るだけで、次の回に届かない。master に残らないもの
   （Pull Request の本文の数字の誤り等）は、結果に書くだけでよい。Pull Request の範囲の外のものは、上の「範囲の外の気づき」のとおり行き先か直さない理由を付けてから 5 へ進む。

5. 満たしていれば、マージの前に、1 で確かめて満たしていた完了の条件へ issue の本文でチェックを付ける（本文をファイルに書いて
   `GH_TOKEN=$FLOW_BOT_TOKEN gh issue edit <番号> -R ridecompass/ride-compass-tasks --body-file <ファイル>` で書き戻す）。作る担当が付け漏らした条件・
   開発機の対話のセッションで出た Pull Request の条件は、ここで付けないと本文に届かず、マージでゲートが残りありとして未着手へ戻す。
   付けないのは、確かめの行（`- [ ] ユーザーが確かめる: …`）・マージのあとでないとできない条件・3 と 4 で足した行。4 で閉じるときは
   どの行にも付けない。
   そのあと Pull Request を squash でマージする（`gh pr merge <番号> -R hidakagit/ride-compass --squash`。コードのリポジトリの
   設定で、題名と本文がそのまま master の1つのコミットになる）。CI は 1 で通ったのを見ているので、待たずに打つ。master の CI も
   待たない（ゲートが閉じる）。マージの道具は通っても何も出さないことがあるので、通ったかは
   `gh pr view <番号> -R hidakagit/ride-compass --json state` で `MERGED` が出るかで見て、`OPEN` のままなら打ち直す。

6. master と競合してマージできなければ、`git fetch origin` で今の master を取ってから
   `git -c merge.conflictStyle=diff3 merge origin/master` で取り込み（1 で取った master は古く、その上では競合しないことがある。
   `diff3` は競合の塊に合流点の行を `|||||||` の下に出す）、競合の塊ごとに、合流点の行を両側がどう変えたかで解き方を決める。

- 合流点の同じ行を両側が変えた・消した: 新しい行を書かないと解けない（並べると同じ決まりが2通りに書かれる）。ただし次を
  全部満たす塊は、その申し送りのとおりに解いてよい（名前の付け替えを当てる）。

- issue のコメントの申し送り（「前後関係と組」の「申し送り」）が、その塊の解き方を「どちらの側の行を残し、もう片側の
  どの名前の付け替え（旧の名前 → 新しい名前）を当てるか」の形で名指している。

- もう片側の行が、合流点の行から旧の名前を新しい名前へ置き換えただけで、ほかの文字が変わっていない。

- 解いた行が、残す側の行の旧の名前を新しい名前へ置き換えただけで、ほかの文字が変わっていない。

どれかに当たらない塊（処理を変える行が要る・申し送りが名指していない・名指した解き方が上の形でない）は、新しい行を書かないと
解けないものとして扱う。照らすのは競合の表示（両側と合流点の行）と解いた行だけで、中身の良し悪しは判じない。

どの塊も上までで解けたら、「競合を解く」のとおりに解き、`git push origin orch/tasks-<番号>` で push し、
作る担当の5と同じく実行を待って必須のチェックを見てから、5 のとおりマージする
（両側の変えた行がどれもそのまま残るので、確かめた中身と master の変更はどちらも書いたとおりに残る。確かめ直さず、並べたことで
壊れたものは必須のチェックで見る）。名前の付け替えを当てた塊があれば、マージの前に、塊ごとのファイルと行・残した側・当てた
付け替え（旧 → 新）・名指した申し送りのコメントへのリンクを、issue にコメントで書く（見出し「競合を解いた照らし」。2 の結果は
先に書いてあるので、別のコメントにする）。新しい行を書かないと解けない塊が1つでもあれば、`git merge --abort` で戻し、どのファイルの
どこが重なったかを書いて「競合」として閉じる（4 と同じ。作る担当が取り込んで出し直す）。

**競合を解く**（作る担当の 1・確かめる担当の 6）: 競合したファイルを開き、`<<<<<<<`・`|||||||`・`=======`・`>>>>>>>` の印と
残さない行（`diff3` なら合流点の行も）を編集で消してから `git add <ファイル>` と `git commit --no-edit`。git checkout の `--ours`・`--theirs` は使わない（判定役に断られる）。

- push・gh の書き込みが GitHub の側の失敗（`remote: Internal Server Error`・`! [remote rejected] … (Internal Server Error)`・
  `GraphQL: Something went wrong while executing your query` 等の 5xx）で落ちた: 2分おいて同じコマンドを打ち直す
  （`sleep 120; <落ちたコマンド>` の1行。Bash の `timeout` を上限の 600000 にする）。ほかのコマンドを続けて書かない（下の「1行に続けて打って」に当たる）。
  gh の書き込み（コメント・本文の書き換え等）は、打ち直す前に書けていないかを読んで見る（落ちたと出ても書けていることがあり、
  コメントを打ち直すと二重になる）。push は同じ枝へ打ち直しても重ならない。打ち直すのは10回まで（間を含めて20分強）。使い切ったら、
  push していない変更とコミットの ID・落ちたコマンドと最後に出た文言を issue にコメントで書いて終える（そのコメントも落ちたら書かずに終え、
  最後の発言に同じことを書く。後始末が終わりのコメントへ写す）。そのあとは担当の種類で分かれる（「担当のワークフローの1回」の4）。
  作る担当なら、push していない変更は後始末が `wip/tasks-<番号>-<時刻>` の枝へ残し、PR も問いも出していないので保留へ動かす。
  保留から出すのはユーザーで、次の作る担当が `wip/` の枝から続ける（作る担当の1）。確かめる担当なら、後始末はタスクを動かさず、
  検証中のまま次の確かめる担当が起こし直される。GitHub の公式の文書（「Best practices for using the REST API」）は 5xx の打ち直しの間と回数を決めて
  いない（「Do not ignore errors」が、続く 4xx・5xx を無視しないことだけを書く）ので、間と回数はこの手順が持つ。

- 日常の操作を1行に続けて打って判定役に断られた: 1つずつに分けて打ち直す。

- 打ち直しても日常の操作が断られたら、回り込まず（別の道具・別の名義で打たない）、`autoMode` の説明を直す（「改善を起票する」）。

- ユーザーの判断が要るところは「問い」の形で書いて `ask.js` で問い、そこで終える（答えは次の起動で拾われる）。
  作る前に、答えの無い判断（方針・見た目の案・本番への書き込み等）が残っていないかを見て、残っていれば問いに要る分だけを
  調べて（画面を撮る・件数を数える等）作らずに問う。作り込んだあとに問うと、答えしだいで作ったものが無駄になる。
  規模の札と、実際に要る作業が一段以上ずれると分かったときも、作らずに問う（その作業に価値があるか）。実際に要る作業は、
  調べて分かった作業に「規模の札」の見込みの数え方（①〜③）を当て直して見る。ただし、ずれが
  答え（補足で範囲を広げた・ほかのタスクを寄せた）の広げた範囲から来るなら、答えを広げた分も含めてやる判断と読んで問わずに
  作り、規模の欄を見込みで付け直して（`field.js <番号> 規模 <S|M|L>`）経緯に書く。作り終えてから（5 の増減で）ずれが
  分かったときは、問わず、欄も付け直さない（「規模の札」）。
  書き込みを断られたファイルの変更は、「担当が書けないファイル」のとおり開発機へ返す。
  答えの補足が問いや提案の直しを求めていたら、直して問い直す。前提（blocked by）が見送りで閉じていたら、進める前に問う。

4. `tasks#<番号>:` の件名でコミットし、`git push origin orch/tasks-<番号>` で push する（断られたら、まず「担当の変更でない断り」に
   当たるかを見る。GitHub の 5xx で断られたときの打ち直しもそこにある）。静的検査とテストを手元で回す場面と範囲と、
   コミットの前に frontend で変えたファイルへかける整形は、testing-operations.md「手元の検査の回し方」だけが決め、全体は CI に任せる。作業ブランチの強制 push は
   コードのリポジトリの規則で断られる（一度 push したコミットは、ほかの者のものも消せない）ので、直しは足すコミットにする。
   master に入るコミットは、5 の Pull Request の題名と本文から作られる（確かめる担当が squash でマージする）。CI は 5 の
   Pull Request の実行だけを待つ（作業ブランチへの push で走るかは testing-operations.md「検査の置き場（手元・作業ブランチのCI・masterのCI）」）。

**担当の変更でない断り**: 操作が、担当の変更の中身でなく、打ち方か作業ブランチの古さか GitHub の側の一時の失敗で断られたときは、担当が理由を除いて
打ち直して進める（開発機へも返さない）。見分けは、断られたものが担当の変更（自分の差分 `git diff --name-only origin/master...HEAD`
と、書こうとしたファイル）に当たるかで、当たれば「担当が書けないファイル」へ進む。

**自動で進めないもの**: 本番 DB へ書く・本番のデータや設定を消す・取り消せない操作は、担当がしない（本番の接続情報も持たない）。
要るときは、書く中身（打つスクリプト・対象・前後に読んで比べるもの）を作業ブランチか issue のコメントに置き、「開発機が要る」の
とおり返す。開発機の対話のセッションが「本番へ書く」のとおり進める。ユーザーに打たせる問いにしない。
Claude が持たない権限の操作（クラウドの画面・外部サービスの登録・GitHub のリポジトリの設定やトークン）だけは、`ask.js` で問う。
問いの文の頭に「PC での操作:」と書き（スマホで問いの1行目を見て、PC が要ると分かるように）、判断材料に手順と確かめ方を書く。
済んだら次のステータスを未着手に、できなければ補足に理由を、と判断材料に書く。未着手で答えが来たら、Claude が確かめ方のとおりに
確かめ、完了の条件にチェックを付ける。

**担当が書けないファイル**: Claude Code の自動モードの判定は、CLAUDE.md・`.claude/` の設定・権限（`.github/claude-task/settings.json`）・
流れの手順（flow.md 等）の編集を、自分を動かす設定の書き換えとして断ることがある（1か所目が通っても次から断られる。判定役への
説明が日常の作業と教えていても、回によって断られる）。断られたら回り込まず（別の道具・写しの差し替え・別の名義で書かない）、
パッチにもせず、「開発機が要る」のとおり返す。書けた分は作業ブランチへ push し（push も断られたら、後始末が `wip/` の枝へ残す）、
何をどこまで書いたかをコメントに書く。開発機の対話のセッションが続きを書く。

#### 開発機の対話のセッション

開発機の対話のセッション（と、それが任せる裏の作業役）も、上の「作る担当」「確かめる担当」の手順で進める。違うのは環境だけで、
違いは次の表のとおり。表に無いことは担当と同じ。

| 項目 | 担当（Actions） | 開発機の対話のセッション |
|---|---|---|
| タスクを持つ | 担当のワークフローが持つ（「1つのタスクを触るのは1者だけ」） | `hold.js` で持つ（下の「持つ」） |
| 進行中へ動かす | 引き受ける段（`claim.js`）が動かし、着手のコメントを書く | 持ってから `move.js <番号> 進行中 <理由>` で、理由のコメントを付けて動かす（作業時間の記録の入りになる。「様子を見る」） |
| 依存 | 担当のワークフローが入れてある（作る担当の2） | 要る道具を動かすとき（画面を撮る・testing-operations.md「手元の検査の回し方」の場面で検査やテストを回す等）だけ、作業ツリーごとに `npm ci --prefix frontend` から入れる（docs/architecture/setup.md「作業ツリーどうしで node_modules を共有しない」）。backend は testing-operations.md「開発機でのbackendテストの回し方」 |
| マージ | 確かめる担当がマージする | ユーザーの指示があれば、対話のセッションがマージする。ワークフローのファイル（`.github/workflows/`）を変える Pull Request は、開発機の gh のトークンに `workflow` の権限が無いので、ユーザーがブラウザでマージする |
| 答え | 回答フォーム（「問い」） | ユーザーがチャットで決めたことを、Claude が issue に記録する（「答え」） |

| 決まり | 出どころ | 担当の読み方 | 開発機の対話のセッションの読み方 |
|---|---|---|---|
| 常時の決まり・規約・手順 | CLAUDE.md と、そこから指す docs/ | 連携がリポジトリの設定を読む（連携の既定の `settingSources` が `user`・`project`・`local`）。指示は読む節を指すだけ（「担当」の3） | Claude Code がリポジトリの CLAUDE.md を読む |
| 権限（自動モード・拒否の一覧・判定役への説明） | `.github/claude-task/settings.json`（master の版） | 連携の `settings` | セッションの始まりのフックの `settings.js`（「担当の権限」） |

- **裏の作業役に任せる**: その場で手順を書き起こさず、作る担当（確かめるなら確かめる担当）の手順のとおりに進めるよう渡し、
  作業役は `hold.js`・`move.js`・`ask.js` を打たない（タスクは対話のセッションが持つ）、とだけ足す。

| 項目 | 担当（Actions） | 開発機の対話のセッション |
|---|---|---|
| 本番 | 接続情報を持たない。読むのも書くのも、要れば「開発機が要る」で返す（「自動で進めないもの」） | 接続情報があり、読める（`run_probe.py`）。書くのは、ユーザーがチャットで言ったときだけ（下の「本番へ書く」） |

- **本番へ書く**: 本番へ書く操作（本番 DB へ書く・本番のデータや設定を消す等）は、対象・中身・差（前 → 後）をチャットで見せ、
  ユーザーがその操作を書くようチャットで言ったときだけ、Claude が自分で打つ。打つスクリプトは開発機の `C:\Users\h7g4b\ride-compass-ops\`
  （コミットしない）へ置く。打ったあと、前後に読んで比べるもの（分布・`run_probe.py` の読み取り等）を読んで確かめ、ユーザーの言葉と
  結果を「答え」のとおりタスクの issue に記録する。

#### 改善を起票する

担当は、手順を進める中で流れそのもの（この文書の手順・`tools/flow-gate` の道具・担当のワークフロー・検査）の改善点に当たったら、
終える前にタスクとして起票する。控えや報告に書くだけにしない——担当の出力はログに残るだけで誰も読まないので、issue に
しないものは次の回に届かない。

- **重ねない**: まず `git fetch origin` のあと、直す場所を今の master の版（`git show origin/master:<パス>`）で読み直し、既に直って
  いれば起こさない——作業ツリーの版は着手したときの master で、そのあとにマージされた直しが見えず、その直しの issue は閉じていて
  次の探し方に当たらない。直っていなければ、直す場所が同じ開いた issue を探す（探し方は「前後関係と組」の「探す」）。直す場所が同じ issue があれば、症状が違っても新しく起こさず、
  起きたこと（日時・作業中の issue の番号・打ったコマンドと出た値）と、同じ直す場所に当たる別の症状であることをその issue へ
  コメントで足すだけにする。寄せた先が前提待ち・保留でも寄せる（そこが直れば消える）。寄せた症状まで直すかは、寄せた先の作る担当が
  [fixing.md](../../.claude/rules/fixing.md)「直し方」の「範囲は性質から導く」で決める。重なった回数は、ユーザーが採否を決める材料になる。

- **書き方**: 「issue の形」のとおりに本文をファイルへ書き、hidakagit-bot の名義で起こす
  （`GH_TOKEN=$FLOW_BOT_TOKEN gh issue create -R ridecompass/ride-compass-tasks --type 保守 --title <題名> --body-file <ファイル>`。
  道具の失敗なら種類は不具合）。背景の節に、どの issue の作業中に・何を打って・何が出たか（観測値）を書き、やることで直す場所を
  名指す（後の担当がその名前で探して当たるように）。規模と優先度は
  `field.js` で入れる（「ラベルと種類と欄」の「規模の札」「優先度の見積もり」）。ほかの開いた issue との前後関係と組も探して張る（「前後関係と組」）。

#### 様子を見る

- **動いている担当**: コードのリポジトリの Actions の画面（Claude Task の実行。名前は「#<番号> <種類>」）。GitHub のスマホアプリの
  Actions からも見られる。振り出しが何を起こしたかは Claude Dispatch の実行の記録に出る。

- **ゲートの失敗**: ゲートは状態を守ることだけをし、出来事の処理の例外は Cloudflare の記録（Workers の Logs）にだけ残す。

- **気づける範囲**: Claude の番のタスクが長く止まる・仕事があるのに担当が動かない・動かしているものが失敗する、のどれかが起きたら、
  ユーザーは上の状況の更新（At risk）か、保留への移動（後始末が担当者をユーザーにする）か、GitHub の Actions の失敗の知らせで気づける。
  原因ごとに見張りを足さず、この症状で拾えるものだけを守る。

- **見回りが失敗し続ける**: 状況の更新を書くのが見回り自身なので、状況の更新には出ない。`coordinator.watchFailMinutes` のあいだ
  1周も通らなければ見回りの実行が失敗で終わり、失敗の知らせで気づける（上の「担当」の「見回り」）。

- **守らないもの**（気づけないまま残す）:

- 規模の欄が空か、その規模に完成の実績が無いタスクが長引く: 想定が無いので「想定を超えたタスク」に出ない。規模を入れれば出る。

- 振り出せる未着手が起きない（起こした担当の実行が GitHub の側で待ちのまま動かず枠を埋める等）: 未着手で待つ時間は数えず、待ちの
  実行は動いている担当に数えるので、どの印にも出ない。Actions の画面では待ちの実行として見える。

- ゲートの失敗そのもの: ステータスが止まった結果として上の印に出るものだけを拾う。

#### 案

- **案**: 「A と B のどちらにするか」を決めてほしいときだけ書き、要らなければ節ごと省く。選んだ案は答えに残り、行き先は次の
  ステータスで別に選ぶ。

- **案**: 自分の領分（どう直すか・書き方）を案に入れない。案の文と実際に当てる作業を一致させる。

#### 段階に分ける

- 道具は段階を親を付けたまま作り（作ってから親を付けると、Project に入った時点で段階と分からず採否の問いが付く）、
  前の段階を blocked by にする（前の段階が閉じるまで見回りが振り出さない）。Project へは「Auto-add sub-issues to project」が
  入れ、ゲートが入口で未着手・Claude にし、優先度に親の値を入れる（段階は同じ仕事を分けたものなので、親に付けた重さを継ぐ）。規模は `field.js` で入れる。
  種類（Issue types）は、道具が作るときに親と同じものを付ける（親に種類が無ければ付けない）。

- 段階を作るときは、兄弟の段階どうしの直す場所（「前後関係と組」の「探す」）を照らし、重なるなら後が先の中身に依るかを見て、
  依るものだけを前後関係の向きで先の段階を後の段階の前提にする（`stage.js` の「前の段階の番号」で渡す）。同時に作った段階は
  互いを照らされないまま並び、中身に依る段階どうしが並んで片方が作り直しになる。
  前提を張るのは、後の段階が前の段階の中身に依る（前の段階の結果しだいで後の段階の書き換えが変わる・前の段階の成果が後の段階の
  材料になる。「前後関係と組」の前後関係）ときだけにする。直す場所が重なっても中身に依らない重なり（生成物・同じファイルの
  別の行や別の節。「前後関係と組」の「中身に依らない重なりは張らない」）は前提を張らずに並べる——張ると見回りが1件ずつしか
  振り出さず、並べて進められる段階が前の段階の終わりを待つ。「念のため」「層の順に」は張る理由にしない。

- **寄せる先**: ある段階の書き換えをほかのファイル（上の入口のテスト等）へ寄せるかもしれないときは、寄せる先のファイルを対象に
  含む段階どうしだけを前後の候補にする。対象に含まないなら、寄せる書き込みは起きないものとして張らない。作る途中で寄せることに
  なったら、その段階の作る担当が寄せる先を自分の直す場所に足して「前後関係と組」の「探す」のとおり照らし、重なる開いた段階のうち
  中身に依るものと張る。

- 親の作業ブランチ（`orch/tasks-<親の番号>`）に push 済みの変更があれば（分ける前の回が作り始めていた）、段階の1つへ渡す。
  親は Pull Request を出さずに閉じるので、渡さないと変更が master へ届かない。渡す先は、その変更を含める段階のうち前の段階を
  持たないもの（ふつうは最初の段階）にする。段階を作ったあと、親の作業ブランチに今の master を取り込み（`git merge origin/master`）、
  `git push origin HEAD:refs/heads/orch/tasks-<段階の番号>` でその段階の作業ブランチとして置き、段階の本文のやることに載せた
  コミットの ID を書く（段階の番号は作るまで分からないので、`stage.js` のあと本文を `gh issue edit` で書き直す）。段階の作る担当は、
  「作る担当」の1の、作業ブランチが GitHub にあるときの手順で続ける。

- 段階は1件ずつ、自分の作業ブランチ（`orch/tasks-<段階の番号>`）と Pull Request で進む。段階が全部閉じると親の前提が閉じ、
  見回りが親を作る担当へ渡す。作る担当は、段階で確かめていない親の完了の条件を確かめて閉じる（「作る担当」）。

#### 前後関係と組

別々に起きたタスクどうしの関係は、GitHub の標準の依存関係（blocked by・blocking）だけで持つ。張った関係は issue の右の
「Relationships」に出て、前提の開いた issue にはボードと Issues の一覧で「Blocked」の印が付く（公式の文書「Creating issue
dependencies」）。前提が開いている未着手は、見回りが飛ばす（`dispatch.js --dry-run` で見られる。ゲートは前提を見ない。「ステータスと割り当て」）。

- **前後関係**（後の作業が先の中身に依る: 先の結果しだいで後の成果が要らなくなる・作り直しになる・後の判断の材料が狂う）:
  後の issue に先を blocked by で張る
  （`GH_TOKEN=$FLOW_BOT_TOKEN gh issue edit <後> -R ridecompass/ride-compass-tasks --add-blocked-by <先>`。起こすときは `GH_TOKEN=$FLOW_BOT_TOKEN gh issue create -R ridecompass/ride-compass-tasks --blocked-by <先>`）。
  張ったら、張った理由（重なった直す場所の名前と、後が先のどの中身に依るか）を後の issue に1行書く（起こすときは本文のやることの
  最後、あとから張るときはコメント。段階の「前提を張った理由」と同じ）。理由が読めないと、マージで重なりが消えたかを後から判じられない（「確かめる担当」の3）。

- **中身に依らない重なりは張らない**: 直す場所が重なっても、後の作業が先の中身に依らないなら前提にせず並べて進め、後から
  マージされる側が「競合を解く」のとおりに合わせる。前提は、先の作る担当・CI・確かめる担当の1往復を後に待たせ、鎖になると
  先頭の1往復が後ろの全部を遅らせる。競合で増えるのは、重なった2件の間の1往復まで。中身に依らない重なりの例:

- **向き**: 片方の結果しだいで他方の成果が要らなくなる・作り直しになるなら、要らなくする側を先（前提）にする。同じ所を触るので
  ぶつからない順に並べたくなる場面でも、この向きを優先する（逆にすると、要らなくなる側を先に仕上げてしまう）。どちらの結果も
  相手の作業に効かないなら、前提にしない（上の「中身に依らない重なり」）。ただし相手が
  既に検証中（Pull Request を出した）なら、相手を先にする（自分を相手の blocked by にする）。確かめる担当は前提を問わず振り出される
  （「担当」の「振り出す条件と順」）ので、検証中の側を後にしても先にマージされ、マージのあとの残りがあって未着手へ戻ると、張った側が閉じるまで
  振り出されなくなる。

- **申し送り**（ほかのタスクに、その範囲で決めてほしい・済ませてほしいこと）: 相手の issue へコメントで書き、相手の本文（完了の
  条件）は書き換えない。本文はそのタスクを進める担当が書き直す（作る担当の6・確かめる担当の3）ので、ほかの者が同時に書くと片方の
  書き込みが消える。相手の作る担当が着手する前なら着手のときに読まれ、着手より後に届いたものは確かめる担当が完了の条件へ足す
  （「確かめる担当」の3）。

- **検証中に張られた側**: 作る担当は、報告（作る担当の6）の前に `GH_TOKEN=$FLOW_BOT_TOKEN gh issue view <番号> -R ridecompass/ride-compass-tasks --json blockedBy,blocking`
  で、Pull Request を出したあとに自分と前後関係を張られていないかを見る。張られていれば、どちらの向きでも問わず（検証中から出すのは
  Pull Request の出来事に任せる。「Claude がステータスを動かす」）、張った側の issue へ申し送りとして、自分の Pull Request の番号と、
  それがどのファイルのどこを変えたかを書く。張った側の作る担当は、それを読んで同じ所の書き換えをマージのあとの master に合わせる
  （「競合を解く」）。

- **重なった行の解き方**: 相手と同じ行を変えていて、相手が後からマージされると分かっているときは、重なる所ごとに解き方を書く。
  解き方が「どちらの側の行を残し、もう片側のどの名前の付け替え（旧の名前 → 新しい名前）を当てるか」で言えるなら、その形で
  ファイルと行・残す側・旧 → 新を名指す。この形のものだけは、相手の確かめる担当がマージの直前の競合をそのとおりに解いてマージする
  （「確かめる担当」の6）。処理を変える行が要るなら、その旨と中身を書く（相手の作る担当が取り込んで解く）。解き方の申し送りは
  依頼ではないので、確かめる担当は完了の条件へ足さない（「確かめる担当」の3）。

- **探す**: 起票するとき（「改善を起票する」も）・作る担当が着手するとき・段階に分けるときに、自分の**直す場所**（変える所。
  ファイル・道具の関数・設定の項目・手順の節。同じ派生の段・同じモジュール・同じ本番の作り直しもその例）を1行で書き、その名前
  （パス・道具名・節の名前）と題名の語で開いた issue を探す（本文のやること・背景がパスや節を名指すので、題名より当たる）。
  当たったものは題名と本文を読んで判じ、同じ直す場所に触るものがあれば前後関係（後が先の中身に依るときだけ）か組を張り、
  張った関係と理由を起票の本文か自分のタスクの issue への報告に書く。重なっても中身に依らないので張らなかったものも、その理由を
  同じ所に1行書く。何も無かったときも、探した鍵
  （直す場所と検索した語）を報告に1行書く（探したかが後から読めるように）。

- **打ち方**: 語1つにつき1回、`GH_TOKEN=$FLOW_BOT_TOKEN gh issue list -R ridecompass/ride-compass-tasks --state open --limit 1000 --search '"<語>" in:title,body'`
  を Bash で打つ（Windows PowerShell 5.1 は引数の中の `"` を落として、囲まない語として届ける。公式の文書 about_Parsing
  「Passing arguments that contain quote characters」）。

- **語を `"` で囲む**: 囲まない `lost_constraints` は、その名前を題名・本文に持つ issue の多くに当たらない。囲むと `_`・`/`・`.` 等で
  区切られた語の並びとして当たる。日本語の語も、囲まないと関係の無い issue まで緩く当たる。

- **`in:title,body` で絞る**: `in` を省くとコメントまで探す（公式の文書「Searching issues and pull requests」の「Search by the
  title, body, or comments」）。確かめる担当の報告等のコメントは多くの道具の名前を書くので、コメントで当たった issue が
  直す場所の重なりを埋もれさせる。

- **パスは最後の名前で打つ**: 囲んだパスは、そのパスを全部書いた issue にしか当たらない（`"lost_constraints"` は
  `backend/scripts/lost_constraints.py` を書いた issue にも当たるが、逆は当たらない）。名前が別の文字と続けて書かれた所
  （区切りの無い所）には当たらないので、0件でも重なりが無いとは言い切らない。

- **語を空白で並べない**: 空白は AND として扱われ、すべての語を持つ issue にしか当たらない（公式の文書「Filtering and searching
  issues and pull requests」の「Building advanced filters for issues」）。

- **`--limit` を付ける**: 付けないと30件で黙って切れる（`gh issue list --help` の `--limit`）。

- 着手したタスクに、まだ閉じていない前提が見つかったら、張ったうえで問う（未着手の答えなら、前提が閉じるまで待つ）。
  答えが前提を張って待つことを求めた（張るのが答えのあと）なら、答えで未着手になった時点では前提が無いので、見回りがすぐ作る
  担当へ振り出す。その担当は前提を張り、Pull Request も問いも出さずに終える（後始末が開いた前提を見て未着手へ戻す。「担当」の
  「担当のワークフローの1回」の4）。
  自分のタスクがほかの issue の先に当たるなら、張るだけで続ける。

- 着手のあとでほかの担当が自分のタスクに前提を張ったら、上の「向き」と同じ基準で決める。前提の結果しだいで自分の作業が
  要らなくなる・作り直しになるなら、自分で見つけた前提と同じに扱って問う。同じ文書の行が重なるだけ（前提の中身に依らない）なら
  問わずに、前提が変える行を避けて進める（重なった行は、後からマージされる側が「競合を解く」のとおりに合わせる）。そう判じた
  理由（何が重なり、なぜ中身に依らないか）を自分のタスクの issue の経緯に書く。

#### 保留と棚卸

- **保留に入る道**: 回答フォームの次のステータス「保留」（補足が答えのコメントに残る）・ユーザーがボードで保留へ動かす（表にある FROM から）・
  `move.js <番号> 保留 <理由>`（担当のワークフローの後始末が、PR も問いも出さずに終わった作る担当を止める。理由がコメントに残る）。

- **保留する判断・実行の書き方**: Claude が保留にするとき（`move.js` の理由・保留を選びうる問いの判断材料）の決まり。ユーザーが
  ボードで保留へ動かすときは理由を求めない（ゲートは表で照らして通すだけで、何も書かない）。理由が要るのは再開を決めるユーザー
  自身なので、書くかはユーザーが決め、理由の無い保留をずれとして挙げない。Claude が書くときは、「後で判断」等の一言メモで済ませず、影響範囲（保留することで何がブロックされるか・何が
  動かなくなるか）と、保留し続けた場合に次に何が起きうるかを書く。置き場は、その判断・実行が属するタスクの issue で、問いを書いて
  問う。すぐには答えられない・時期が来ていないなら、そのことと再開の条件を判断材料に書く。属するタスクが無いときだけ新しい
  issue にする（判断を待つためだけに issue を作らない）。

- **日付で再開するものは保留にしない**: 再開の条件が日付だけで決まるもの（日付から導けるもの・外の出来事を決まった日に見に行くものも）は、
  保留にせず未着手＋着手可能日（「ラベルと種類と欄」）で待つ。振り出しは未着手と検証中だけを見るので、保留に入れた日付は来ても
  誰も拾わない。保留は、人の判断か、日付で見に行けない外の出来事を待つものに限る。

- **棚卸**（ボード）: 未着手の列へ動かす → Claude の番・完了の列へ動かす → 完成（完了の条件が残っていれば戻る）・`Close as not planned` → 見送り・
  回答待ちの列へ動かす → ゲートが問いを置き、回答フォームで次のステータスと補足を返す（確かめだけが残るなら、完成で残りにチェックを付けて閉じる。
  「ステータスと割り当て」の「問い」）。

#### issue の形

| 順 | 節 | 答える問い | 書くもの | 書かないもの |
|---|---|---|---|---|
| 5 | 完了の条件 | 何を満たしたら閉じるか | 外から確かめられる形のチェック（`- [ ]`。本文のチェックはここにだけ使う。チェックの無いものが残るとゲートは閉じない）。マージの時点で確かめられることだけを書く（ユーザーの確認は `- [ ] ユーザーが確かめる: …` の行）。Actions の担当が確かめられる形で書く: 開発機にしか無いもの（「担当」の「開発機が要る」）で確かめる条件は、同じことをテスト DB・CI で確かめる形（前後の SQL 文の比べ・テストの期待値等）で書き、書けなければ起票のときにラベル「開発機が要る」を付ける（マージのあとの残りにだけ要るなら付けない。確かめる担当の3） | 手段。マージのあとにしかできない作業（本番での操作・公開・長い観測）は、自動にするか別の issue にして blocked by でつなぐ（待つ日があれば、その issue に着手可能日を入れる） |
| 7 | 規模の根拠 | 規模の札の根拠 | 札と根拠1行 | ― |

- `<details>` の中は、`<summary>` の行のあとに空行を1つ入れてから書く（入れないと Markdown が効かない）。

- 問いに答えが出たら、Claude は 4 からその行を消し、6 へ1行足す（本文だけ読めば今の状態が分かるように）。

- **誰がやっても同じ品質になるように書く**。会話でしか共有していない判断基準・母集団の決め方・完了の条件は、別セッションには
  届かない（記憶はリポジトリの外にあり、別環境では消える）。そのタスクを実行する人が、対象をどう列挙し、何を満たせば完了で、
  何を根拠に残す/消すを決めるのかを、issue だけ読んで再現できる状態にする。「実測して判断する」と書いたなら、何をどう測るかまで書く。

- **直す範囲を母集団で決めるタスク**は、背景かやることに母集団を [fixing.md](../../.claude/rules/fixing.md)「直し方」の「範囲は性質から導く」の
  4つの欄（性質・道具・拾わない形・検算）で書き、完了の条件は同じ節の「検証は別の入力で行う」のとおり、母集団を決めた道具の
  0件だけにしない。

- **規模M以上のタスクは、着手したら最初に背景・方針を issue に書く**。作業内容が変わりうる大きめのタスクほど、途中で背景・方針判断が
  失われやすく、後から遡って書くと経緯（なぜその設計にしたか）が失われる。

#### ラベルと種類と欄

- 1つのタスクに1つの値を持つもの（Status・優先度・規模）は、Project の単一選択の欄に置く。スマホの GitHub アプリでも
  issue の ⓘ →「プロジェクト」に出る（組織の issue fields は出ないので使わない）。優先度は仕事としての重さの見積もりで、
  入っている値は誰かが決めた値（ユーザーが付けた・Claude が起票で下の「優先度の見積もり」のとおり入れた・段階が入口で親から継いだ）だけで、
  誰も決めていない欄は空のまま見せる（入口が既定で埋めると、起票の直後に入れた値を読んでから書くまでの間に消す）。`field.js` は入っている
  値の書き換えを断る（変えるならユーザーに問う）。振り出しはその選択肢の順に並べ、空は `flow.config.json: unsetPriority` の位置に置く。
  `field.js` は、起票の直後でまだ Project に入っていない issue なら、入るまで待ってから書く。規模は Claude が `field.js` で入れる。今の値は値を渡さない
  `field.js <番号>` で読む（書かずに、Status を含む全部の欄を出す。`gh issue view --json projectItems` は Status しか出さない）。
  欄は機械が決めるものなので、回答フォームには出さない（ユーザーが直すときはボードで）。選択肢を足せば並べ順はそのまま効く。

- ラベルはユーザーが付ける札（例: 急ぎ）。状態・操作待ちのように、ステータスと問いで表せるものはラベルにしない。「急ぎ」はユーザーの「急いで」の依頼で、振り出しは優先度の欄より先に並べる。「開発機が要る」は担当かユーザーが付け、振り出しはそのタスクを飛ばす（「担当」）。回答フォームは、置き場に定義されたラベルを
  名前を持たずに全部出す。規模の決め方は下の「規模の札」。前提は blocked by で付ける（「前後関係と組」）。

- **規模の札**は、結果の変更の広がりで決まる: 実装＋テストの変更行（追加＋削除、生成物を除く）が200以下ならS・
  1000以下ならM・超えればL。実装とテストはコードのファイルで、CI・デプロイ・担当の手順そのものであるワークフローを含み、
  設定（JSON・YAML 等）を含まない（分け方は `scripts/review_checks.py: change_kind` が総量の計測と共に持つ）。本番DBへ書くタスク（移行ファイルを足す・本番で書き込む）は行数によらずL。Project の欄「規模」（S・M・L）は
  起票時の予想で、起票の本文に根拠を1行添える——①調べないと分からない部分は先に調べる段階として切り、その段階はS
  ②本番DBへ書く予定ならL。ファイルを置き換える作業（テストの起こし直し等）は、③より先に、置き換えるファイルの今の行数×2
  （旧版の削除と新版の追加）を変更行の見込みとして、上の変更行の閾値で札を決める。置き換えずに1本ずつ見て減らす作業（テストの
  見直しで消す・まとめる等）は、同じく③より先に、対象のファイルの今の行数（`wc -l`。空行・コメントを含む）の4分の1を変更行の
  見込みとする（消す行はファイル数に比例せず、作り終えるまで測れないため。4分の1は済んだ見直しの変更行の、今の行数に対する
  割合の中ほど） ③それ以外は変わると見込むファイル数（テストを含み文書を除く。契約を変えるなら読む側も数える）が
  7以下ならS・20以下ならM・超えればL。欄は見込みのまま残し、作り終えたあとの実際の変更行（`python scripts/review_checks.py change`
  が出す札）で付け直さない——欄は作業時間の想定（「様子を見る」の「想定を超えたタスク」）を見込みの札ごとに作るためのもので、
  実際の札は Pull Request の本文の増減に残る。見込みと実際の札の差は、見込みの数え方を見直す材料になる。

- **優先度の見積もり**: Claude が起票するときは、Project の欄「優先度」を仕事としての重さで見積もり（`field.js <番号> 優先度 <高|中|低>`）、
  規模の根拠の節に理由を1行添える。高は利用者に届いている不具合・データの誤り・止まっている流れ、低は調べ・整理・見た目の小さな直し、
  それ以外は中。ユーザーの「急いで」はラベル「急ぎ」で、見積もりとは別に振り出しが先に並べる。
