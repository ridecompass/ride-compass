# タスクの流れ

## 原則

流れ（タスクの進め方・ゲート・担当・道具・この手順書と流れのスキル）の決まりは、次の6つから導く。各節の先頭の「導く原則」は、
その節の決まりをどの原則から導いたかを示す。

1. **ユーザーの手は、判断と最後の確かめだけ**: ユーザーに求めるのは、何を作るか・どちらの案にするかの判断と、本番での最後の確かめだけ。操作（PC での作業・パッチ当て・本番への書き込み）は求めない。ただし Claude が打てない操作（本番のデータを完全に消す・外部の画面でのアカウント作成等）だけは、打つものを用意して頼む。
2. **回答待ちは、答えられる状態のときだけ**: 問い・答える中身（本番に出ていること）・回答フォームがそろってから、回答待ちにする。
3. **状態は1か所・動かす道は1つ**: タスクの状態の正本は1つで、同じ状態を複数の経路で書かない。
4. **詰まりは見ればわかり、あとから判断できる**: どのタスクが止まっていて、何を（誰を）待っているかが、聞かなくても一目でわかる。終わった作業は、あとから判断できる記録（担当の実行の全文・修正前後のキャプチャ・測り直した値）を残す。
5. **守るのは、利用者に見える結果**: テストも見張りも、利用者に見える壊れを先に守る。部品の内側の細部は後。
6. **例外は原則を直して扱う**: 原則に合わない場面が出たら、手順書や流れのスキルに例外を足さず、原則を見直す。原則から導けない決まりは書かない。

## 流れのあらまし

導く原則: 3。

タスクは GitHub の issue で、大きすぎるものは、要望ごとに切り出すか、1つの要望を機能ごとに子（sub-issue）へ分ける（.claude/skills/file-issue/SKILL.md「分ける」）。
ステータスは Project の欄「Status」に置き、**ゲート（`tools/flow-gate/`）が事実から1つの決め方で決める**（`tools/flow-gate/src/decide.js: decide`）。
事実は、issue（開き閉じと閉じた人・完了の条件・問いと答え・前提・着手可能日時）・作業ブランチの Pull Request（下書きか・CI・差し戻し・
マージのコミットの CI）・担当が付いているか。同じ事実からは何度決めても同じで、ゲートは今の値と違う所だけを書く。Claude はステータスを書かない。
それぞれの状態で何をするかは、この文書と流れのスキル（`.claude/skills/` の task-work・ask・file-issue・dev-session）が決める。

## 置き場と役割

導く原則: 1・3。

| 置き場・役 | 持つもの・すること |
|---|---|
| 置き場のリポジトリ（`flow.config.json: tasks`）と2つのボード（`flow.config.json: boards`） | タスクの issue・問いと答え・記録（記録は issue にだけ持ち、git に写さない）。Actions のボードは担当が進めるタスク、対話作業のボードは種類「対話作業」（`flow.config.json: dialogType`）の、開発機の対話のセッションだけが進めるタスク |
| ゲート（Cloudflare の Worker。Webhook を受ける `ridecompass-gate` と、Access の内側の回答フォーム `ride-compass-answer`） | 出来事と定時に事実を読み、ステータス・担当者・本文の先頭のボタン・ボード・種類を書き、子の印と孫の外しをする。見回りが担当を振り出す。回答フォーム |
| Claude（hidakagit-bot の名義） | 作業・問いとコメント・分けることと前提・確かめとマージ・欄の規模と優先度と着手可能日時 |
| ユーザー（hidakagit） | 判断（回答フォームか、開発機の対話のセッションのチャット）・本番での最後の確かめ・保留と完了・ラベル（`急ぎ` 等） |

ゲートは自分の書き込み（送り主 `flow.config.json: gateBot`）を無視する。issue を種類でボードへ入れるのもゲートで、種類は作るときに決まり、
対話作業の境目をまたいで変えるとゲートが戻す。

## ステータスと割り当て

導く原則: 1・2・3・4。

決め方の正本は `tools/flow-gate/src/decide.js: decide` で、ここには読み方を書く。

- **保留と完了だけは、ユーザーの決定も受ける**（ボードの移動・閉じる・問いへの答え・チャットの答えの記録）。保留は、ユーザーが置いたら出すまで保つ
  （持っている担当の実行は取り消す）。完了は、完成（完了の条件が全部済んだ）か見送り（Close as not planned）でだけ受け、条件が残ったまま完成で
  閉じる・完了へ動かすと、ゲートが事実へ戻す（tasks#788「完了の条件が残ったまま完成にさせない」）。ほかのステータスは事実から決まり、
  ユーザーが動かしてもゲートが事実へ戻す。Claude は保留と完了を自分の判断で書かない（止める・終えるのはユーザーの決定。原則1）。
- **誰の番か（2階）**: ゲートの決め方は2階で、1階が成果物の事実と関係性からステータスと「待っているか」を決め、2階がその結果だけを
  読んで担当者を決める。担当者は2択で、ユーザーに問わないと進めないもの（回答待ち・保留）はユーザー、ほかは Claude（hidakagit-bot）、
  完了は無し（手で変えても、その出来事でゲートが戻す）。待っているのは、関係性（前提・子が開いている・着手可能日時が先・親が保留か閉じた）と、外の事情で振り出せないもの
  （担当の枠が埋まっている・振り出しを止めている）。
- **動きの確かめ**: Claude の番で待っていないのに、最後の動きから `flow.config.json: stallHours` の時間動かなければ、異常として
  イレギュラーを問う（ユーザーの番になり、持っている実行を取り消す。「やり直す」なら振り出し直し、CI待ちのものは、答えのあとに担当の実行が起きるまで作る担当へ渡す形に保つ）。
  最後の動きは、ゲートのほかが書いたコメント・本文の編集・作業ブランチの Pull Request のコミットとマージ・検査の終わり・担当の実行の
  始まりと終わり・issue を作ったときのうち一番新しいもので、GitHub と見回りの記録から出す。時間の経過は出来事を起こさないので、
  見回りが定時に、ユーザーの番でない開いた issue を、1件ずつゲートに決め直させる（受け箱は1回の起こしで1件ずつ処理する）。担当の1回の実行も
  同じ時間を上限にする（`claude-task.yml` の `timeout-minutes`）。
- **入口**: Claude が起こした要望は、何を作るかがユーザーの判断なので、ゲートが採否を問う。子と、本文に「分割元: #<元>」のある
  切り出しは、採否を親か元から受け継ぐ。ほかは未着手で入る。
- **子**: 子（親を持つ issue）は、優先度・着手可能日時・「急ぎ」・保留を自分の欄でなく親の値で見る。子は完了の条件を持たず、自分の
  Pull Request がマージされ、マージのコミットの master の CI が通れば完了。子が完成で閉じたら、親の条件のうち `- 子: #<子>` の行に印を
  付ける。親が開き直されない閉じ方で閉じたら、開いた子を見送りで閉じる。孫は張られた直後に外して知らせる。
- **待つ相手**: 前提（blocked by）と子は同じに扱う。開いた相手があれば、確かめも完了もせず未着手。見送りか重複で閉じた相手があれば、
  続けるかを一度だけ問う。
- **持たれている間**: 担当の実行（順番待ちを含む）がある間は、作るなら進行中、確かめるなら検証中。
- **ユーザーが書いた文**: 答えの文（決まった形の行のほかの文）とコメントは、ゲートが中身を読まず、Claude が読むまで Claude の番にする
  （閉じたあとの文なら開き直す。閉じるときに一緒に書いた文は閉じる決定の一部）。担当は、終わりのコメントの「読み始め」より前の文を読んでいる。
  保留の間は、保留から出たときに読む。
- **問い**: 最新の「## 問い」が形（.claude/skills/ask/SKILL.md「問い」）に合い、答えが無ければ回答待ち。答えは、見送りなら見送りで閉じ、保留なら保留、確かめの
  「完了にする」なら確かめた行にチェックを付け、ほかは下の決め方へ進む。書いた文のある答えは、Claude が読んだあとに一度だけ当て、当てたことを知らせる。
- **手放したあと**: 作業ブランチの開いた Pull Request は、確かめる担当が下書きへ戻したら未着手、CI が終わるまで CI待ち、落ちたか変異テストに
  新しい生き残りが出たら未着手、通れば検証待ち（下書きならゲートがレビュー可能にする）。確かめる担当がマージも差し戻しも問いもせずに
  手放したら、回答待ちにしてゲートが何が起きたかを問う（イレギュラー）。Pull Request が無ければ、マージのあとの残りはマージのコミットの
  master の CI（デプロイを含む）が終わるまで CI待ち、残りが無ければ完成で閉じ、残りが全部ユーザーの確かめなら回答待ちにしてゲートが確かめを
  問い（本番に出てから問う）、前提が開いているか着手可能日時が先なら未着手。作る担当が何も出さず残りも済ませずに手放したら、イレギュラーを問う。
- **残り**: 本文の完了の条件のうちチェックの無いもの（`tools/flow-gate/src/questions.js: remaining`）。完成は、残りが無くなった事実で
  決まり、ユーザーが基準になる確かめは、その答えが行を満たす。
- **受け入れない書き込み**: 形に合わない問い・印の間の見知らぬ行・形の合わない着手可能日時は受け入れず（読めない着手可能日時はまだ先と読む）、
  ゲートが1つのコメントで知らせる（`tools/flow-gate/src/decide.js: decide`）。書き方はスキルが持ち、守られなかったときをゲートが捉える。
- **本文の先頭**: 回答待ちの間だけ、ゲートが回答フォームへのボタンを置く（印 `<!-- flow-gate -->` の間）。GitHub の画面では本文の下の欄まで
  毎回たどるのが負荷になるので、本文の先頭に置く（ユーザーの決定）。

**1つのタスクを触るのは1者だけ**: 担当は振り出しでだけ起き、同じ issue の実行は担当のワークフローの `concurrency`（`queue: max`）で1本ずつ順に動く。
担当が付いているかは、見回りの1つの記録（`tools/flow-gate/src/patrol.js: Patrol`）だけが持ち、振り出した時点（順番待ちを含む）と
担当の実行の始まり・終わりの知らせで変える。出来事は1つの受け箱（`tools/flow-gate/src/inbox.js: Inbox`）から1つずつ順に処理する。担当の付いたタスクは振り出さない。開発機の対話のセッションは、対話作業の issue を前提に張って持つ（.claude/skills/dev-session/SKILL.md「開発機の対話のセッション」）。

## 担当（Claude が自分の番を進める）

導く原則: 1・3・4・5。

| 役 | すること |
|---|---|
| ゲート（見回りを含む） | ゲートはステータスを決めて書き、見回り（`tools/flow-gate/src/patrol.js`）は担当の記録を持って振り出す |
| 担当のワークフロー（`.github/workflows/claude-task.yml`） | 準備をして担当を起こし、終わったら後始末をする |
| 作る担当・確かめる担当（Claude Code。`anthropics/claude-code-action`） | タスクの遂行と報告（手順は .claude/skills/task-work/SKILL.md）。次の担当を起こすことには触れない |

- **振り出す条件と順**（見回り。`tools/flow-gate/src/patrol.js: Patrol.dispatch`）: 作るは未着手、確かめるは検証待ち。
  前提が開いている・着手可能日時が先・対話作業・担当が付いている、は除く。並びは `急ぎ` → 優先度の選択肢の順（空は `flow.config.json: unsetPriority`）→
  番号の小さい順で、種類ごとの枠（`flow.config.json: slots`。使っている数は記録の担当の数）まで。振り出すのは、担当の実行が終わったとき・決め直したタスクが
  振り出せるステータスにあるとき・定時（`tools/flow-gate/wrangler.toml` の `triggers`。着手可能日時や止めの終わりが来る）。振り出したらその場で決め直す。
- **受け箱**: ゲートは出来事を受け箱へ書いてから受け取ったと返す。一時の失敗は間をあけてやり直し（後ろの出来事は先に進む）、直らない失敗はすぐ諦めて
  状況の更新に出す。GitHub が届けられなかった知らせは送り直されず、その出来事での決め直しは次の出来事まで抜ける（ユーザーの決定で許す）。
- **担当のワークフローの1回**:
  1. 振り出し: 見回りが `workflow_dispatch` で起こす。実行の名前「#<番号> <種類> <振り出しの識別子>」で、見回りがどの振り出しの担当かを読む。
  2. 準備（`.github/workflows/claude-task.yml` の段）。
  3. 担当を起こす。指示は役・作業ツリー・issue の番号と読む節だけを渡し、決まりを写さない。担当は最初の結果で終わり、裏で動かす道具は外してある。
  4. 後始末（落ちても止められても走る）: GitHub に無い変更を `wip/tasks-<番号>-<時刻>` の枝へ残し、手番の記録を置き場のリリース（日ごと）へ置き、
     issue に終わりのコメント（担当の最後の発言・手番の記録・判定に断られた操作・実行）を書く（`.github/claude-task/after.js`）。担当が Claude の
     利用の上限・認証で止まったら、最後の段（`flow.config.json: quotaStep`）を落とす。ゲートは、最後に終わった実行でこの段が落ちていれば、
     その終わりから `flow.config.json: pauseMinutes` の間振り出さない。
- **名義**: 置き場へは hidakagit-bot（`FLOW_BOT_TOKEN`）、コードのリポジトリへは hidakagit（`CODE_TOKEN`。`GITHUB_TOKEN` のマージは master の CI と
  デプロイを起こさない）。届く範囲は docs/architecture/tech-stack.md「秘密の値とトークン」。gh の既定は `CODE_TOKEN`（開発機では hidakagit の
  ログイン）なので、置き場を打つときは読むときも `GH_TOKEN=$FLOW_BOT_TOKEN` を付ける。名義の誤りを止めるのはトークンの届く範囲だけ。
- **止める**: Claude Task を無効にする（`gh workflow disable "Claude Task" -R ridecompass/ride-compass`。戻すのは `enable` で、次の定時から
  振り出す）。担当は打てない。利用の上限の止めを早く解くなら、担当を1件手で起こす。動いている担当は Actions の画面で Cancel する。
  1つのタスクだけなら、ボードで保留へ動かす。
- **開発機でしかできない作業**（開発機にしか無いもの（本番への調べの鍵・開発 DB の実データ）や、担当がしない操作（下の2つ）が要る作業）:
  担当はそこで止め（途中の変更は push してから）、何がなぜ要るかを書いた対話作業の issue を起こして元のタスクの前提に張って終える。
  開発機の対話のセッションがその issue を閉じると、元のタスクがまた振り出される。ユーザーがその issue を起こして引き取ってもよい。

**担当の権限**: 担当は自動モードで動き、判定役には `.github/claude-task/settings.json` の `autoMode` で環境と日常の操作を教える。決して打たせない操作
（master への push・強制の push・`gh api` の書き込み・ワークフローを止める・戻す等）は `permissions.deny`、ユーザーの答えが要る編集（`scripts/size_thresholds.json`）は
`permissions.ask` に置く（各一覧は既定の規則 `$defaults` を必ず残す）。拒否の規則はコマンドの全文に当たるので、規則の頭の道具（`git push`・`gh api`）はつながずに1つで打ち、`gh api` で読むときは
欄を URL に書く。このファイルは担当だけのもので、master の版が次の実行から効く。開発機の権限はユーザー自身の設定が持ち、リポジトリからは書かない
（Claude Code は判定役への説明をリポジトリの設定から読まない。公式の文書「Configure auto mode」）。担当にも開発機にも効かせたい守りは、
GitHub の側（ルールセット・トークンの権限）に置く。日常の操作が断られたら、回り込まずに流れの摩擦として記録する（直すのは `autoMode` の説明）。

**自動で進めないもの**: 本番 DB へ書く・本番のデータや設定を消す・取り消せない操作は、担当がしない（接続情報も持たない）。書く中身（スクリプト・対象・
前後に読んで比べるもの）を作業ブランチか issue に置き、「開発機でしかできない作業」のとおり返す（.claude/skills/dev-session/SKILL.md「本番へ書く」）。
マージの前に済ませる書き込みが要る変更は、Pull Request を出す前に返す。Claude が持たない権限の操作（クラウドの画面・外部サービス・リポジトリの設定やトークン）
だけは問い、問いの文の頭に「PC での操作:」と書き、判断材料に手順と確かめ方を書く。

**担当が書けないファイル**: 自動モードの判定は、CLAUDE.md・`.claude/` の設定・権限・流れの手順の編集を、自分を動かす設定の書き換えとして断ることがある。
断られたら回り込まずパッチにもせず、書けた分を push し、どこまで書いたかを書いて「開発機でしかできない作業」のとおり返す。

## 様子を見る

導く原則: 4。

ボードそのものが様子で、ステータスは事実から決まるので列が実態になる。盤面に表れないゲートの事実（諦めた出来事・振り出しを止めている理由といつまで）は、ゲートがボードの状況の更新に、変わったときだけ書く（`tools/flow-gate/src/gate.js: reportHealth`）。動いている担当は Actions の画面（Claude Task の「#<番号> <種類>」）。
担当が何も出さずに手放すか、Claude の番のまま動かなければゲートが問い（担当者がユーザーになる）、出来事を処理できなければ状況の更新に出し、ワークフローが落ちれば
GitHub の失敗の知らせが届く。この症状で拾えない詰まりは、例外を書き足さず流れの摩擦として記録する。

## コミット

導く原則: 4・3。

**1タスク=1コミット**（子は子ごと）。コミット履歴は、件名と本文だけでどこまで戻せばよいかを特定できる状態に保つ。問い・決定・確認の結果は
issue に書き、git には写さない。master のコミットは Pull Request の題名と本文から作られ、件名は `tasks#<番号>: <何が変わったか（利用者・運用から見た結果）>`
（子はその番号、複数は `tasks#12・tasks#13:`）、本文の形は `.github/pull_request_template.md` だけが持ち、Pull Request の CI が照らす。
属するタスクの無い変更は作らない。

## ゲートを変える・公開する

導く原則: 3・5。

設定は `flow.config.json`、決め方は `src/decide.js`、問いの形は `question_template.md` を直す。master に入ると `claude-gate.yml` の `deploy-gate` が、
master の先頭の版を `wrangler deploy`（Webhook）と `wrangler deploy --env form`（回答フォーム）で公開する（秘密の値の名前は `tools/flow-gate/wrangler.toml` の先頭）。
決め方を変えた直後は、出来事の無い issue が次の出来事まで前の姿で残る。テストは `node --test tools/flow-gate/test/*.test.js`、構文と import の
解決は `npm run lint`（`tools/flow-gate/eslint.config.js`。流れのスキルに同梱したスクリプトも照らす）で、CI（`claude-gate.yml` の `flow-gate`）も同じ2つを流す。
