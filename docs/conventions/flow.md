# タスクの流れ

## 原則

流れ（タスクの進め方・ゲート・担当・道具・この手順書と流れのスキル）の決まりは、次の原則から導く。各節の先頭の「導く原則」は、
その節の決まりをどの原則から導いたかを示す。

1. **ユーザーの手は、判断と最後の確かめだけ**: ユーザーに求めるのは、何を作るか・どちらの案にするかの判断と、本番での最後の確かめだけ。操作（PC での作業・パッチ当て・本番への書き込み）は求めない。ただし Claude が打てない操作（本番のデータを完全に消す・外部の画面でのアカウント作成等）だけは、打つものを用意して頼む。
2. **回答は、答えられる状態のときだけ**: 問い・答える中身（本番に出ていること）・回答フォームがそろってから、ステータスを回答にする。
3. **状態は1か所・動かす道は1つ**: タスクの状態の正本は1つで、同じ状態を複数の経路で書かない。
4. **詰まりは見ればわかり、あとから判断できる**: どのタスクが止まっていて、何を（誰を）待っているかが、聞かなくても一目でわかる。終わった作業は、あとから判断できる記録（担当の実行の全文・修正前後のキャプチャ・測り直した値）を残す。
5. **守るのは、利用者に見える結果**: テストも見張りも、利用者に見える壊れを先に守る。部品の内側の細部は後。
6. **例外は原則を直して扱う**: 原則に合わない場面が出たら、手順書や流れのスキルに例外を足さず、原則を見直す。原則から導けない決まりは書かない。
7. **issue は約束を持って生まれ、約束が全部果たされたら終わる**: 生きている間は、どの状態にも持ち主が1者いて、持ち主は出力を出して次の持ち主へ渡す。親子に関係なく、issue ごとに自分の約束を持ち、自分の約束が全部果たされたら、ステータスに関係なく終わる（完成）。ただし本文の「やること」の項目のうち、行き先（自分の約束・ほかの issue・見送り）を名指していないものが残る間は終わらない（約束の外に残った作業を、黙って捨てない）。やめるのはユーザーだけ（見送り）。
8. **成果物そのものの事実で判じる**: 状態は、それが表す事実そのもので読む。その事実を出すはずの1つの実行の結論のような、代わりの指標で読まない（マージした変更が検査とデプロイを通ったかは、その変更を含む master の実行で読み、マージのコミット自身の実行だけで読まない）。
9. **出力を出せる者にだけ持たせる**: 持ち主は、その状態から出力を出せる者だけにする。出せる者がいないときは、待つ相手（別の issue・ユーザー・開発機・日時）を名指して待ち、待つ相手がユーザーか開発機なら、聞かなくても見える所に出す。持ち主に要る権限は、持ち主を決める決まりと一緒に決める。

## 用語

導く原則: 7。

- **実行**: GitHub Actions のワークフローの実行（workflow run）1回。
- **実行の種類**: 実装担当・検証担当・検査。検査は、Pull Request の CI とマージのコミットの master の CI を含む。
- **実行の status と conclusion**: GitHub の名前と値をそのまま使う。
- **約束**: issue の完了の条件の行。受け入れ条件（ユーザーのもの）と、作る側の完了の定義がある。行に書かれていないもの（マージのコミットの
  検査が通ること等）は約束に数えない。
- **持ち主**: ある状態の issue を、次の状態へ移す責務を持つ者。
- **移管**: 約束の行を、文を変えずに別の issue へ属させ替えること。
- **行き先**: 本文の「やること」の項目が、どの約束で果たされるか（自分の完了の条件の行・ほかの issue）か、やらないこと（見送りと理由）。
  書き方は .claude/skills/file-issue/SKILL.md「issue の形」。

## issue のライフサイクル

導く原則: 7・6。

ステータスの値は、次に結果を出す者の行為（実装・検査・検証・回答・保留・待機・完了）。

**生まれる**

| 生まれ方 | 起こす者 | 生まれたときの約束 | 最初の状態 |
|---|---|---|---|
| ユーザーの起票 | ユーザー | ユーザーが書く受け入れ条件 | 実装か待機 |
| Claude の起票（種類が要望） | Claude | Claude が案として書く受け入れ条件 | 回答（採否） |
| Claude の起票（要望以外） | Claude | 完了の条件 | 実装か待機 |
| 切り出し | 実装担当 | 元から移管した行 | 実装か待機（採否は元から継ぐ） |
| 子 | 実装担当 | 親から移管した機能の行 | 実装か待機（採否は親から継ぐ） |
| 対話作業 | 担当か開発機の対話のセッション | 開発機でしかできない作業の結果 | 実装（持ち主は開発機の対話のセッション）。元の issue の前提に張る |

**生きている間**

| 状態 | 持ち主 | 次の状態へ移る条件 |
|---|---|---|
| 実装 | 実装担当（対話作業は開発機の対話のセッション） | Pull Request を出した → 検査／問いを出した → 回答／待つ相手を張った・着手可能日時を入れた → 待機／約束が全部果たされた → 完了 |
| 検査 | 検査 | Pull Request の検査が合格 → 検証、合格でない → 実装／自分か子の変更を含む master の検査が合格 → 約束の残りしだい、合格でない → 実装 |
| 検証 | 検証担当 | マージした → 検査／下書きへ戻した → 実装／問いを出した → 回答 |
| 回答 | ユーザー | 答えた → 答えに応じた状態 |
| 保留 | ユーザー | 解いた → 事実から決まる状態 |
| 待機 | 待つ相手（前提・子・親・日時） | 相手が閉じた・日時が来た → 事実から決まる状態 |
| 完了 | なし | — |

どの状態でも、約束が全部果たされたら完了へ移る（下の「終わる」）。

**実行の終わり**: 担当の実行は、状態か約束のどちらかが動いていれば正当に終わる。約束が動いたとは、行にチェックが付いたか、移管が
あったこと。どちらも動かずに終われば、イレギュラーとしてユーザーに渡す。

**終わる**: issue ごとに、自分の約束が全部果たされたら、どの時点でも完成で終わる（Pull Request・前提・子・担当の実行・マージのコミットの
検査に関係なく。動いている担当の実行は取り消す）。待つのは、ユーザーが置いた保留と、Claude がまだ読んでいないユーザーの文と、行き先を
名指していない「やること」の項目だけ。行き先の無い項目が残れば、ゲートはそれを知らせて実装担当へ渡す（行き先を書くのは実装担当）。
ユーザーの見送りは約束ごと終わる。親が閉じれば（見送りか、ユーザーが完成で閉じた）、開いた子は見送りで終わる。

## 流れのあらまし

導く原則: 3・7。

タスクは GitHub の issue で、大きすぎるものは、要望ごとに切り出すか、1つの要望を機能ごとに子（sub-issue）へ分ける（.claude/skills/file-issue/SKILL.md「分ける」）。
ステータスは issue の欄（issue fields）「ステータス」に置き、**ゲート（`tools/flow-gate/`）が事実から1つの決め方で決める**（`tools/flow-gate/src/decide.js: decide`）。
事実は、issue（開き閉じと閉じた人・完了の条件・問いと答え・前提・着手可能日時・ラベル・時系列）・作業ブランチの Pull Request（下書きか・差し戻し・master とぶつかっているか）と、
その先頭のコミットとマージのコミットの検査の実行・担当の実行と終わりのコメント。同じ事実からは何度決めても同じで、ゲートは今の値と違う所だけを書く。
Claude はステータスを書かない。それぞれの状態で何をするかは、この文書と流れのスキル（`.claude/skills/` の task-work・ask・file-issue・dev-session）が決める。

## 置き場と役割

導く原則: 1・3。

| 置き場・役 | 持つもの・すること |
|---|---|
| 置き場のリポジトリ（`flow.config.json: tasks`） | タスクの issue・問いと答え・記録（記録は issue にだけ持ち、git に写さない）。ステータス・実行の status・優先度・規模・着手可能日時は組織の issue fields（`flow.config.json: fields`）で issue が持つ。どう見せるか（Project のボード・ビュー・issue の一覧の絞り込み）は GitHub の画面で決め、ゲートは関わらない。種類「対話作業」（`flow.config.json: dialogType`）は、開発機の対話のセッションだけが進めるタスク |
| ゲート（Cloudflare の Worker。Webhook を受ける `ridecompass-gate` と、Access の内側の回答フォーム `ride-compass-answer`） | 出来事と定時に事実を読み、ステータス・欄「実行の status」・担当者・本文の先頭のボタン・問いのラベル・種類を書き、孫を外す。決めたステータスを作業ブランチの Pull Request へ写す（検証で下書きをレビュー可能にし、見送りで閉じる・閉じた issue の Pull Request を閉じる。親が閉じて見送りで閉じる子も同じ）。issue の情報は持たない（事実の持ち主は GitHub）。持つのは、出来事の受け箱と、失効の時刻まで変わらないインストールの鍵だけ。見回りが担当を振り出す。回答フォーム |
| Claude（hidakagit-bot の名義） | 作業・問いとコメント・分けることと前提・確かめとマージ・欄の規模と優先度と着手可能日時・開発機で作業中のラベル |
| ユーザー（hidakagit） | 判断（回答フォームか、開発機の対話のセッションのチャット）・本番での最後の確かめ・保留と完了・ラベル（`急ぎ` 等） |

ゲートは自分の書き込み（送り主 `flow.config.json: gateBot`）を無視する。種類は作るとき（最初に付いた種類）に決まり、
対話作業の境目をまたいで変えるとゲートが戻す。

## ステータスと割り当て

導く原則: 1・2・3・4・7・8・9。

決め方の正本は `tools/flow-gate/src/decide.js: decide` で、ここには読み方を書く。

- **保留と完了だけは、ユーザーの決定も受ける**（ステータスの欄を変える・閉じる・問いへの答え・チャットの答えの記録）。保留は、ユーザーが置いたら出すまで保つ
  （持っている担当の実行は取り消す）。完了は、完成（完了の条件が全部済んだ）か見送り（Close as not planned）でだけ受け、条件が残ったまま完成で
  閉じる・完了へ動かすと、ゲートが事実へ戻す。ほかのステータスは事実から決まり、ユーザーが動かしてもゲートが事実へ戻す。
  Claude は保留と完了を自分の判断で書かない（止める・終えるのはユーザーの決定。原則1）。
- **誰の番か（2階）**: ゲートの決め方は2階で、1階が成果物の事実と関係性からステータスを決め、2階がその結果だけを読んで持ち主（次に結果を
  出す者）を1つの決め方で決め、担当者と振り出しをそこから導く（`tools/flow-gate/src/decide.js: dispatchKind`）。持ち主は、ユーザーに問わないと
  進めないもの（回答・保留）はユーザー、検査・待機は事実が動くのを待つ Claude、実装・検証は、対話作業とラベル「開発機で作業中」
  （`flow.config.json: devLabel`）のある issue なら開発機の対話のセッション（ラベルが無い間はユーザー）、ほかは担当、完了は無し。担当者は2択で、持ち主がユーザーなら
  ユーザー、ほかは Claude（hidakagit-bot）、完了は無し（手で変えても、その出来事でゲートが戻す）。ステータスは対話作業でも事実どおり（検査の間は検査）。
- **待機**: 次に結果を出すのが担当（実装・検証）でも、待つ相手（前提・子が開いている・着手可能日時が先・親が保留か閉じた）がある間は待機。
  待つ相手は、約束が残っている間に問う・振り出す時機を待つためのもので、完了は止めない（上の「終わる」）。子は親の要望を機能ごとに分けた
  部分なので、開いた子がある間は親の確かめを問わない。見送りか重複で閉じた相手があれば、続けるかを一度だけ問う（種類「続行」の問い。ゲートは事実を見つけて問うだけで、決めるのはユーザー）。見回りは待機を振り出さない。
  前提の対話作業は開発機の対話のセッションしか進めないので、果たし忘れると、待っているタスクは待機のまま止まる。止まった対話作業は、待っている側ではなくユーザーの番の一覧に出る（下の「様子を見る」。原則9）。
- **欄「実行の status」**: ステータスが指す種類の、動いている実行の status を GitHub の値のまま写す（無ければ空。表示のためだけで、決め方には使わない）。
  検査は、検査のワークフロー（`flow.config.json: checks`）の最も新しい実行の status（題名・説明文を書き直すと同じコミットで打ち直し、前の実行は取り消されて残る）。
- **作業の上限**: 担当の1回の作業は3時間まで（`claude-task.yml` の `timeout-minutes`。ジョブが始まってからの正味の時間）。超えると GitHub が実行を取り消し、
  状態も約束も動かさずに手放したことになって、ゲートがイレギュラーを問う。ゲートは時間を測らない。順番待ちの長さは、欄「実行の status」の queued で見える。
- **入口**: Claude が起こした要望は、何を作るかがユーザーの判断なので、ゲートが採否を一度問う（採否の問いがあるかは、issue のコメントで見る）。
  子と、本文に「分割元: #<元>」のある切り出しは、採否を親か元から受け継ぐ。
- **子**: 子（親を持つ issue）は、優先度・着手可能日時・「急ぎ」・保留を自分の欄でなく親の値で見る。約束（完了の条件）は自分の本文に持ち（原則7）、
  ほかの issue と同じく、自分の約束が全部果たされたら完了。親が開き直されない閉じ方で閉じたら、開いた子を見送りで閉じる。
  孫は張られた直後に外して知らせる。
- **持たれている間**: 担当の実行（順番待ちを含む）がある間は、その担当の種類（実装か検証）。
- **ユーザーが書いた文**: 答えのコメントの欄の文とコメントは、ゲートが中身を読まず、Claude が読むまで Claude の番にする
  （閉じたあとの文なら開き直す。閉じるときに一緒に書いた文は閉じる決定の一部）。担当は、終わりのコメントの「読み始め」より前の文を読んでいる。対話作業とラベル「開発機で作業中」の issue は、開発機の対話のセッションが読んでから書くので、
  Claude のコメントより前の文を読んでいる。
  保留の間は、保留から出たときに読む。
- **問い**: 最新の「## 問い」に答えが無ければ回答。読めない問い（.claude/skills/ask/SKILL.md「問い」の読める前提に外れたもの）も答えを待ち、回答フォームは
  読めない理由を出して、回答内容を出さずに書く欄と次遷移で答えを受ける。答えの無い問いが残っていても、約束が全部果たされたら完成で閉じる（上の「終わる」）。ゲートが出した問い（ラベルの形の「出す者」がゲートのもの）は、同じ事実から決め直して同じ問いが出る間だけ読み（一度問うたこと・担当の実行・保留・読まれていない文は、問いを出す事実に数えない）、出なくなったら読まずに下の決め方で決める。担当が出した問いは、ゲートが中身を読まないので答えまで読む。担当の終わりのコメントは、そのあとに答えがあれば答えで扱ったものとして、終わり方を判じ直さない。
  答えの決定は、答えの「次遷移:」の行（続ける・保留・見送り）だけで決まり、回答内容（選んだ案・済ませることの値・コメント）は遷移先が読み、ゲートは
  読まない（確かめることの値は、回答フォームが本文の約束へユーザーの名義で書く）。見送りなら見送りで閉じ、保留なら保留、続けるなら遷移先の Claude が答えを
  読むまで実装（約束が全部果たされていれば完成で閉じる）で、読んだあとは下の決め方へ進む。書いた文のある答えは、Claude が読んだあとに当て、当てたことを一度だけ知らせる。答えのあとにユーザーがステータスを変えたか開き直したら
  （issue の時系列の事実）、その答えは当てない。ゲートが出す確かめの問いの確かめることには、ユーザーが確かめる条件ごとに、条件の文と行の下の「見る所と要点」が並ぶ
  （無い条件は「書かれていません」と出る）。答えの無い問いがある間（本文の先頭に回答のボタンがある間）は、ゲートがラベル「問い: <ラベル>」を付け、
  答えが当たるか問いが要らなくなったら外す（一覧で、誰に何を問うているかが見える）。
- **手放したあと**: 作業ブランチの開いた Pull Request は、検証担当が下書きへ戻したか、master とぶつかっている（GitHub の計算中は数えない）なら
  実装（取り込むのは実装担当で、検証担当を起こしてもマージの手前で戻すだけになる）、検査が終わるまで検査、合格なら検証（下書きなら
  ゲートがレビュー可能にする）、合格していなければ（不合格か、検査の実行が1本も無い）実装（検査が始まる形で push するのも直すのも実装担当）。
  合格は、検査のワークフローの最も新しい実行が終わり、その結論が GitHub が必須の検査の合格に数えるもの（成功・スキップ・中立）であること。結論は、
  Pull Request では必須の検査（`ci-ok`）と同じで、マージのコミットではデプロイも含む（コードのリポジトリのルールセットは `ci-ok` の合格を求め、
  最新の master の取り込みは求めない。求めると1件入るたびにほかの Pull Request が全部載せ直しになる。組み合わせで壊れたものは master の CI が捕まえ、通るまで本番へ出ない）。ほかのワークフローの実行（担当の実行・必須でない検査）は数えない。
  本番に出たかは、自分か子の変更を含む master の検査の実行で読む: 件名がその番号の実行のうち一番新しいものより後に作られた push の実行が、終わって
  合格していれば出た（原則8。master の後のコミットは前の変更を全部含む。`tools/flow-gate/src/facts.js: deployOf`。親は子の変更が本番に出るまで待つ。
  一時の失敗は、後の実行が通れば覆うので、打ち直さない）。変異テストの生き残りはゲートが読まず、検証担当が読んで、扱われていなければ下書きへ戻す。
  Pull Request が無ければ、マージのあとの残り（子のマージを待つ親も）は、その変更を含む master の検査（デプロイを含む）が通るまで検査（落ちても実装へ戻さない。
  落ちた理由がこの変更の誤りかをゲートは見分ける事実を持たず、この issue の担当にはできることが無いことが多い。原則9。master の最新のコミットの検査が落ちたら、
  ゲートが「master の検査が落ちている」の issue を1件だけ起こし（開いていれば使い回す。`tools/flow-gate/src/gate.js: masterFailure`）、落ちた master はその担当が直す）、
  残りが無ければ完成で閉じ、残りが全部ユーザーの確かめなら回答にしてゲートが確かめを問う（本番に出てから問う）。
  担当が手放したとき、次に結果を出すのが手放した担当と同じ種類のまま（状態が動かず）、その実行で約束も動いていなければ、イレギュラーを問う（その実行の間に前提を張って待つ相手を名指したなら、動いたに数える）。
  約束が動いたかは、担当の終わりのコメントの「読み始めの完了の条件」と今の本文を比べて決める（チェックが増えたか、消えた行が全部その実行の間にできた
  移管先にある）。
- **残り**: 本文の完了の条件のうちチェックの無いもの（`tools/flow-gate/src/questions.js: remaining`）。完成は、残りが無くなった事実で
  決まり、ユーザーが基準になる確かめは、その答えが行を満たす。
- **受け入れない書き込み**: 読めない問い（回答内容を無いものとして答えを受ける）・印の間の見知らぬ行・形の合わない着手可能日時は受け入れず（読めない
  着手可能日時はまだ先と読む）、ゲートが1つのコメントで読めない理由を知らせる（`tools/flow-gate/src/decide.js: decide`）。書き方はスキルが持ち、
  守られなかったときをゲートが捉える。
- **本文の先頭**: 回答の間だけ、ゲートが回答フォームへのボタンを置く（区切りの注 `<!-- flow-gate -->` の間）。GitHub の画面では本文の下の欄まで
  毎回たどるのが負荷になるので、本文の先頭に置く（ユーザーの決定）。
- **読む値の鮮度と要求の数**: ゲートは、変わりうる値（issue・Pull Request・検査・実行の一覧・開いた issue の一覧）を出来事1件の処理の中でだけ使い、
  次の出来事では読み直す。1件の決め直しは、事実を読む1回と、本文・欄・担当者・ラベル・種類・コメント・Pull Request の操作・閉じるをまとめた
  書き込み1回（GitHub は1回の要求に並べた書き込みを並べた順に行う）と、取り消す実行ごとに1回（Actions の取り消しには1回にまとめる口が無い）。
  当て直すと結果が変わる答え（保留・見送り）があるときは答えより後の時系列を、担当が約束の行を消して終えたときは移管先の候補を、それぞれ1回読み足す。
  定時は、担当の実行の一覧と開いた issue の一覧を1回ずつ読み、振り出しと決め直す番号の列挙の両方に使う。

**1つのタスクを触るのは1者だけ**: 担当は振り出しでだけ起き、同じ issue の実行は担当のワークフローの `concurrency`（`queue: max`）で1本ずつ順に動く。
担当が付いているかは、GitHub の担当のワークフローの実行の一覧（`tools/flow-gate/src/facts.js: recentRuns`。終わっていない実行）から、決め直すたびに読む。
同じ issue の実行が2本以上あれば（振り出した直後で一覧にまだ出ていない間に、もう一度振り出した等）、ゲートがいちばん古いものを残してほかを取り消す。出来事は1つの受け箱（`tools/flow-gate/src/inbox.js: Inbox`）から1つずつ順に処理する。担当の付いたタスクは振り出さない。開発機の対話のセッションは、触るタスクにラベル「開発機で作業中」を付けて持つ（.claude/skills/dev-session/SKILL.md「開発機の対話のセッション」）。

## 担当（Claude が自分の番を進める）

導く原則: 1・3・4・5・7。

| 役 | すること |
|---|---|
| ゲート（見回りを含む） | ゲートはステータスを決めて書き、見回り（`tools/flow-gate/src/patrol.js`）は担当の記録を持って振り出す |
| 担当のワークフロー（`.github/workflows/claude-task.yml`） | 準備をして担当を起こし、終わったら後始末をする |
| 実装担当・検証担当（Claude Code。`anthropics/claude-code-action`） | タスクの遂行と報告（手順は .claude/skills/task-work/SKILL.md）。次の担当を起こすことには触れない |

- **振り出す条件と順**（見回り。`tools/flow-gate/src/patrol.js: dispatch`）: ステータスが実装なら実装担当、検証なら検証担当。

  振り出せるステータスにあるとき・定時（`tools/flow-gate/wrangler.toml` の `triggers`。着手可能日時や止めの終わりが来る）。並びが読むステータスは前に決めた値なので、

- **受け箱**: ゲートは出来事を受け箱へ書いてから受け取ったと返す。一時の失敗は間をあけてやり直し（後ろの出来事は先に進む）、直らない失敗はすぐ諦める。

- **担当のワークフローの1回**:
  1. 振り出し: 見回りが `workflow_dispatch` で起こす。実行の名前「#<番号> <種類> <振り出しの識別子>」で、見回りがどの振り出しの担当かを読む。
  2. 準備（`.github/workflows/claude-task.yml` の段）。
  3. 担当を起こす。指示は役・作業ツリー・issue の番号と読む節だけを渡し、決まりを写さない。担当は最初の結果で終わり、裏で動かす道具は外してある。
     担当が待つときは、終わるまで前に出したまま待つ（裏で動かしたシェルは実行の終わりの数秒後に止まり、裏の知らせで起こし直されることも無い）。
  4. 後始末（落ちても止められても走る）: GitHub に無い変更を `wip/tasks-<番号>-<時刻>` の枝へ残し、手番の記録を置き場のリリース（日ごと）へ置き、
     issue に終わりのコメント（担当の最後の発言・手番の記録・判定に断られた操作・実行・読み始め・読み始めの完了の条件）を書く（コードのリポジトリは
     公開で実行の記録は誰でも読めるので、担当の出力は非公開の置き場にだけ置く。`.github/claude-task/after.js`。
     担当が作業ブランチへ移っても振り出された版で動くよう、ワークフローが実行の始まりに写した道具で打つ）。担当が Claude の

  書いた文と読み、ユーザーにも通知が届かない。名義の誤りを止めるのはトークンの届く範囲だけ（gh はトークンをホストごとにしか選べず、拒否の規則は

- **開発機でしかできない作業**（開発機にしか無いもの（本番への調べの鍵・開発 DB の実データ）や、担当がしない操作（下の2つ）が要る作業）:
  担当はそこで止め（途中の変更は push してから）、何がなぜ要るかを書いた対話作業の issue を起こして元のタスクの前提に張って終える。

**担当の権限**: 担当は自動モードで動き、判定役には `.github/claude-task/settings.json` の `autoMode` で環境と日常の操作を教える。決して打たせない操作

欄を URL に書く。このファイルは担当だけのもので、master の版が次の実行から効く。開発機の権限はユーザー自身の設定が持ち、リポジトリからは書かない
（Claude Code は判定役への説明をリポジトリの設定から読まない。公式の文書「Configure auto mode」）。担当にも開発機にも効かせたい守りは、
GitHub の側（ルールセット・トークンの権限）に置く。日常の操作が断られたら、回り込まずに流れの摩擦として記録する（直すのは `autoMode` の説明）。

**自動で進めないもの**: 本番 DB へ書く・本番のデータや設定を消す・取り消せない操作は、担当がしない（接続情報も持たない）。書く中身（スクリプト・対象・
前後に読んで比べるもの）を作業ブランチか issue に置き、「開発機でしかできない作業」のとおり返す（.claude/skills/dev-session/SKILL.md「本番へ書く」）。

**担当が書けないファイル**: 自動モードの判定は、次の種類の操作を断ることがある（括弧は断られた例。1か所目が通っても次から断られることがあり、回によって違う）。起票では、やることがこの種類に当たるかを見て
分ける（.claude/skills/file-issue/SKILL.md「起票する」）。

| 種類 | 例 |
|---|---|
| 担当自身を動かすファイルの編集 | CLAUDE.md・`.claude/` の設定・権限・流れの手順、担当のワークフロー（`.github/workflows/claude-task.yml`）と後始末の道具（`.github/claude-task/after.js`）、ゲートの道具（`tools/flow-gate`）の一括の書き換え |
| 本番へ出すジョブの編集 | `.github/workflows` のデプロイのジョブ |
| 取り消せない操作 | 置き場の欄を消す（`gh project field-delete`）、作業ツリーのファイルを一時に書き換えて戻す確かめ |
| 共有の置き場・遠隔への書き込みと実行 | 本物の置き場への試しの push、本番の backend へ向けた playwright の実行、issue のコメントから取り出したコードの実行 |

読むだけの操作（`sed`・`git stash list`・`gh variable list` 等）が断られるのは判定への説明の足りなさで、この種類に入れず流れの摩擦として記録する
（直すのは「担当の権限」の `autoMode` の説明）。断られたものが自分の変更（`git diff --name-only origin/master...HEAD` と書こうとしたファイル）に
当たらない断り（打ち方・作業ブランチの古さ・GitHub の一時の失敗）は、理由を除いて打ち直して進める。自分の変更が断られたら回り込まずパッチにもせず、書けた分を push し、どこまで書いたかを書いて「開発機でしかできない作業」のとおり返す。

## 様子を見る

導く原則: 4・9。

issue の欄と担当者そのものが様子で、ステータスは事実から決まるので実態になる。動いている担当は Actions の画面（Claude Task の「#<番号> <種類>」）。

- **ユーザーの番**: ゲートが担当者をユーザーにした issue で、GitHub の issue の一覧では `is:issue is:open assignee:hidakagit` で絞る。答えるもの（回答・保留）は `field.ステータス:回答,保留`、開発機で進めるもの（ラベル「開発機で作業中」の無い対話作業）は `type:"対話作業" field.ステータス:実装,検証` を足して分ける（欄の値は引用符で囲まない。欄の絞り込みは GitHub の新しい検索だけが受ける）。
- **開発機が持っている**: ラベル「開発機で作業中」の issue（`label:"開発機で作業中"`）。持ち終えたらラベルを外す（.claude/skills/dev-session/SKILL.md「開発機の対話のセッション」）。
- **開発機の対話のセッションの始まり**: フックが `scripts/review_checks.py: cmd_turns` を打ち、上の2つを、ステータスと種類で分けて出す。行には、答えを待つ問いのラベルと、最後のコメントがゲートの知らせ（行き先が無くて閉じない等）ならその1行目を添える。誰の番かはゲートが決めた担当者とラベルで読み、一覧の側で決め直さない。

担当が何も出さずに手放すか、Claude の番のまま動かなければゲートが問い（担当者がユーザーになる）、ワークフローが落ちれば
GitHub の失敗の知らせが届く。この症状で拾えない詰まりは、例外を書き足さず流れの摩擦として記録する。

## コミット

導く原則: 4・3。

**1タスク=1コミット**（子は子ごと）。コミット履歴は、件名と本文だけでどこまで戻せばよいかを特定できる状態に保つ。問い・決定・確認の結果は
issue に書き、git には写さない。master のコミットは Pull Request の題名と本文から作られ、件名は `tasks#<番号>: <何が変わったか（利用者・運用から見た結果）>`
（子はその番号、複数は `tasks#12・tasks#13:`）、本文の形は `.github/pull_request_template.md` だけが持ち、Pull Request の CI が照らす。
属するタスクの無い変更は作らない。

## ゲートを変える・公開する

導く原則: 3・5。

設定は `flow.config.json`、決め方は `src/decide.js`、問いの形は `question_forms/` の種類ごとのファイルを直す（種類を足したら `src/config.js` にも並べる）。master に入ると `ci.yml` の `deploy-gate` が、
master の先頭の版を `wrangler deploy`（Webhook）と `wrangler deploy --env form`（回答フォーム）で公開する（秘密の値の名前は `tools/flow-gate/wrangler.toml` の先頭）。
決め方を変えた直後は、出来事の無い issue が次の出来事まで前の姿で残る。構文と import の
解決は `npm run lint`（`tools/flow-gate/eslint.config.js`。流れのスキルに同梱したスクリプトも照らす）で照らし、CI（`ci.yml` の `flow-gate`）も同じものを流す。
**ゲートと流れのスキルに同梱したスクリプトには、テストを書かない**（`.claude/rules/testing.md` の「挙動を変えたら、入口で確かめる」も当てない）。
ゲートは GitHub を読んで書くだけで、GitHub の代わりを作ると実装をもう一度書くことになり、守るものの無いテストがコードより速く増える。
確かめは lint と、変えたあとに本番の issue で起きた動きで行う。
