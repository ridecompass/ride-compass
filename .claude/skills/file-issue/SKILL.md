## 流れの摩擦を記録する

導く原則: 6・3。

流れ（`docs/conventions/flow.md`・流れのスキル・`tools/flow-gate`・担当のワークフロー・検査）で困ったことに当たっても、起票も、その場だけの直しもしない。
直すのは周期レビューで、摩擦を集めて原則から全体で決める（`.claude/commands/review.md`「流れの摩擦を集める」）。

- **書くもの**: この回に実際に起きたことだけ（打った道具が断った・失敗した、手順に無い・手順どうしが食い違う場面で自分で決めた、
  同じ長いコマンドを組み立て直した、待ちが作業より長かった）。観測の無い思いつきは書かない。
- **書き方**: 作業中のタスクの報告（担当は終え方の要約）に、頭を「流れの摩擦:」にした行を1件1行で、手順のどこで・打ったコマンドと出た値を書く。

## 起票する

導く原則: 3・4・7。

- **今の差分で直せるものは直す**（CLAUDE.md「作業ツリーの安全」の「新しいタスクは…」）。
- **重ねない**: 直す場所（変える所。症状でなく、どこを変えれば消えるか）を1行で書き、`git fetch origin` のあと今の master で読み直して、
  直っていれば起こさない。直す場所が同じ開いた issue（「前後関係と組」の「探す」）があれば、症状が違っても起こさず、起きたこと
  （日時・作業中の issue・打ったコマンドと出た値）をそこへコメントで足す。寄せた症状まで直すかは、寄せた先が [fixing.md](../../rules/fixing.md)「直し方」で決める。
- **担当で進められない操作を分ける**: やることが `docs/conventions/flow.md`「担当が書けないファイル」の種類か「自動で進めないもの」に当たれば、
  種類を対話作業にする。担当で進められる部分と混ざるなら、当たる部分を対話作業の issue に分けて前提に張る（「分ける」の「開発機でしかできない作業」）。
- **書き方**: 「issue の形」の本文をファイルに書き、
  `node .claude/skills/file-issue/scripts/new-issue.mjs --type <種類> --title <題名> --body-file <ファイル> --size <規模> --priority <優先度> [--blocked-by <前,...>] [--start <着手可能日時>]`
  で起こす（形と欄を照らし、合わなければ作らずに合わない所を返すので、直して打ち直す）。前後関係と組を張り（「前後関係と組」）、起こした番号を自分のタスクの報告に書く。
- 入口はゲートが決める（`docs/conventions/flow.md`「ステータスと割り当て」の「入口」）。Claude が起こした要望は、ゲートが採否を問う。

## issue の形

導く原則: 4・3・7・1。

**題名**は、何をするか（何が困るか）だけを30字前後で。**本文**は次の節をこの順に並べ、1 以外は `<details><summary>節の名前</summary>`
（summary の行のあとに空行）で畳む。節ごとに答える問いは1つで、当たらないものはその節に書かない。並べるものは箇条書きか表にする。

| 順 | 節 | 答える問い | 書くもの |
|---|---|---|---|
| 1 | 要約（畳まない） | 開いて2行で何が分かるか | 何が起きていて、何をするか |
| 2 | 不具合: 起きていること／要望: 困りごと／保守: 背景／調査: 明らかにしたいこと | なぜやるのか | 事実（不具合なら再現の手順と、期待する動き・実際の動き）。保留中は最後に再開の条件。案は書かない |
| 3 | やること（調査は: 調べ方） | どうやるのか | 案と手段を番号付きで。やることの項目には、行の下に字下げして `- 行き先: ` を書く（下の「やることの行き先」） |
| 4 | 決めること | まだ決まっていないことは何か | 1行ずつ。答えが出たら消して 6 へ1行足す。無ければ省く |
| 5 | 完了の条件 | 何を満たしたら閉じるか | 外から確かめられる `- [ ]` の行（本文のチェックはここにだけ使う）。確かめる者は既定で Claude。ユーザーが確かめる条件は、行の下に字下げして `- 確かめる: ユーザー` と `- 見る所と要点: <見る先へのリンク>。<何が作られ・何が分かったか>`（下の「ユーザーが確かめる条件」）。1つの約束は、その issue の持ち主の出力だけで果たせるように書く（ほかの issue の出力が要るなら、行の中に入れず前提か子で持つ） |
| 6 | 経緯 | いつ何が決まり、何が変わったか | 日付つきで1行ずつ、新しいものを上に（問いと答えの全文は写さない） |
| 7 | 規模と優先度の根拠 | 札と見積もりの根拠 | それぞれ1行 |

- **完了の条件は、マージの時点で Actions の担当が確かめられる形で書く**: 開発機にしか無いもので確かめる条件は、テスト DB・CI で確かめる
  形（前後の SQL 文の比べ・テストの期待値等）で書き、書けなければ対話作業の issue を起こして前提に張る（「分ける」の「開発機でしかできない作業」）（マージのあとの残りにだけ要るなら起こさない）。
  マージの前に済ませる本番への書き込み（.claude/rules/deployment-sync.md「コミットと同時に揃えるもの」）は、済ませたことを条件の1行に書く。
  本番での前後の比べは、何をどう測るかを書いたマージのあとの残りの1行にする（前の値はマージの前に検証担当が取る）。マージのあとに
  しかできない作業（本番での操作・長い観測）は、自動にするか別の issue にして blocked by でつなぐ。
- **やることの行き先**: 項目（節の中の字下げの無い番号付きの行）ごとに、どこで果たすかを `- 行き先: 完了の条件「<条件の文の頭>」`（自分の
  完了の条件の行。文の頭は今の条件の文に当たること）・`- 行き先: #<番号>`（ほかの issue へ寄せた・分けた）・`- 行き先: 見送り（<理由>）`（やらないと
  決まった。ユーザーの答えか、要らないと分かった事実を理由に書く）のどれかで書く。起票のときに決まらなければ、着手した実装担当が書く。
  行き先の無い項目が残る間は、完了の条件が全部済んでもゲートが完成で閉じず、知らせて実装担当へ渡す（`tools/flow-gate/src/questions.js: unboundSteps`）。
- **ユーザーが確かめる条件**: テスト・CI・Claude の確かめで合否が決まる条件には付けず、ユーザーが見て決めるもの（見た目・使い心地・目的に
  合うか・本番の実物）だけに付ける。確かめる時点でユーザーが見て決められるものにする。前の状態との比べ（前より速い等）のように比べる相手が
  残らないものや、確かめるのに取り消せない操作（答えを送る等）が要るものは置かず、測れるなら Claude が前後を測る条件にする。見る所と要点は、ゲートが確かめの問いに条件ごとに写すので、本文を開かずに答えられる中身にする。
  条件を足した者が先に見る先と見るべき点を書き、作った担当が Pull Request を出すときに見る先（Pull Request・撮った画面・結果の節）で埋める。
- **本番で人が見つけた不具合**は、2 に拾えなかった層（CI のテスト・e2e・e2e-live・デプロイの確かめ等）ごとに、何を見ていてなぜ見なかったかを1行書く。
- **誰がやっても同じ品質になるように書く**: 会話でしか共有していない判断基準・母集団の決め方・測り方も書き、issue だけで再現できるようにする。
  1つの Pull Request に収まらない・方針を選ぶタスクは、着手したら最初に背景・方針を書く。
- **長く残る形は、作る前に合意する**: 新しい表・保存の鍵・公開する API の形（作ったあとに変えると、本番の作り直しか読む側の書き換えが要るもの）を
  作るタスクは、起票か着手の最初に、やることへ設計の項を書く——近い仕組み（同じ事実・同じ用途を持つ表・鍵・API）との関係、今の用途の
  ほかに使われうる用途、あとから変える費用。書いたら作らずに、形の候補を案にした問い（.claude/skills/ask/SKILL.md「問い」のラベル「判断」）で
  合意を取る。名前を並べただけのものは設計に数えない。分けるときは、子を起こす前に取る（子の担当に形を決めさせない）。
- ユーザーが GitHub の画面でテンプレートから作った issue（節が `###` で並ぶ）は、着手するときにこの形へ整える。

## ラベルと種類と欄

導く原則: 3・1・4。

- 種類は Issue types（不具合・要望・保守・調査・対話作業）で、1つのタスクにちょうど1つ。ステータスは issue の欄「ステータス」だけが持ち、
  ゲートが決める。ラベルはユーザーが付ける札（`急ぎ` は振り出しを優先度より先に並べる）で、状態や操作待ちには使わない。
- **欄**（規模・優先度・着手可能日時。issue の欄（issue fields）で、回答フォームには出さない）: Claude が書くのは、起票の
  スクリプトの `--size`・`--priority`・`--start`。起こしたあとに入れ直すなら `node .claude/skills/file-issue/scripts/new-issue.mjs --fill <番号> [--size …] [--priority …] [--start …]`。
- **優先度の見積もり**: 入っている値は誰かが決めた値なので書き換えない（変えるならユーザーに問う）。Claude は起票のときに仕事の重さで見積もって入れる:
  高は利用者に届いている不具合・データの誤り・止まっている流れ、低は調べ・整理・見た目の小さな直し、それ以外は中。子には入れない
  （ゲートが親の値を読む。「分ける」）。空は振り出しで `flow.config.json: unsetPriority` の位置に並ぶ。
- **規模の札**: 実装＋テストの変更行（生成物・文書・設定を除く。`scripts/review_checks.py: change_kind`）が200以下ならS・1000以下ならM・超えればL。
  本番 DB へ書くタスクはL。起票のときの見込みは、①調べないと分からない部分は、先に調べる調査の issue（S）を起こして前提に張る ②本番 DB へ書くならL
  ③置き換えるファイルは今の行数×2、1本ずつ見て減らすなら今の行数の4分の1を変更行とする ④それ以外は変わるファイル数（契約を変えるなら読む側も、テストも含み
  文書を除く）が7以下ならS・20以下ならM・超えればL、の順で決め、作り終えたあとで付け直さない。
- **着手可能日時**: その時刻より前には振り出さない日本時間（`YYYY-MM-DD HH:MM`。時刻を省けば 00:00）。時間を待つ残り・外部の公開待ち・
  決まった日の作業に使い、その時刻までステータスは待機。形の合わない値はゲートが受け付けず（まだ先と読んで振り出さない）、コメントで知らせる。日付だけで再開が決まるものは保留にせず、これで待つ。
- 状態を動かしただけのコメントは書かない。詳細は `<details>` に入れる。

## 前後関係と組

導く原則: 3・4・7。

タスクどうしの関係は、GitHub の標準の blocked by だけで持つ。前提が開いているタスクは振り出されない。

- **前後関係**（後が先の中身に依る: 先の結果しだいで後が要らなくなる・作り直しになる）: 後に先を blocked by で張り
  （`GH_TOKEN=$FLOW_BOT_TOKEN gh issue edit <後> -R ridecompass/ride-compass-tasks --add-blocked-by <先>`）、理由（重なった直す場所と、後が先のどの中身に依るか）を後に1行書く。
  要らなくする側を先にする。相手が既に Pull Request を出しているなら相手を先にする（検証の側を待たせると、その Pull Request が止まる）。直す場所が重なっても中身に依らない重なり（生成物・同じファイルの別の行や節・先がマージ済みの所）は張らず、
  後からマージされる側が合わせる。
- **組**（同じ本番の作り直し・同じ変更の範囲に触り、別々に進めると作り直しや確かめが2回になる）: 1つの Pull Request に収まるなら1つの
  issue にまとめ（残す側で問い、もう片方の約束の行を残す側へ移管する。行が0になればゲートが閉じる）、収まらないなら先を後の前提にし、本番の作り直しと確かめは後で1回だけ行う。
  親子にはしない。
- **申し送り**（ほかのタスクに決めてほしい・済ませてほしいこと）: 相手の issue へコメントで書き、相手の本文は書き換えない。着手より後に
  届いたものは、相手の検証担当が完了の条件へ足す。
- **探す**: 起票・着手・分けるときに、自分の直す場所を1行で書き、その名前（パス・道具名・節の名前）と題名の語ごとに
  `GH_TOKEN=$FLOW_BOT_TOKEN gh issue list -R ridecompass/ride-compass-tasks --state open --limit 1000 --search '"<語>" in:title,body'` を打って読み、
  同じ直す場所に触るものに前後関係か組を張る。パスは最後の名前で打つ（囲んだパスは、そのパスを全部書いた issue にしか当たらない）。語は空白で並べない（AND になる）。区切りの無い所には当たらないので、0件でも重なりが無いとは言い切らない。張った・張らなかった理由と、探した鍵を報告に1行ずつ書く。
  - 着手したタスクに閉じていない前提が見つかったら、張ったうえで問う。ほかの担当が自分に前提を張ったら、上の前後関係の向きで決め、中身に
    依らない重なりなら問わずに避けて進め、理由を経緯に書く。

## 分ける

導く原則: 4・1・7。

1つの issue が大きすぎるときに、分けて完了させやすくする。分けた1つずつは、Pull Request 1本で完了できる大きさにする。分けるのは
実装担当で、着手してから決める（.claude/skills/task-work/SKILL.md「実装担当」の3）。分け方は下の2つで、どちらに当たるかで形が違う。
分けた issue どうしは、後が前の結果を使うときだけ blocked by を張り（「前後関係と組」。「念のため」「層の順に」は理由にしない）、
後の本文のやることの最後に、張った理由か「前提なし」を1行書く。

### 要望ごとに切り出す（親子にしない）

1つの issue に要望が2つ以上混ざっていれば、元を要望の1つに絞り（本文と完了の条件をその要望のものだけにする）、ほかの要望を別の
issue へ切り出す。ユーザーの答えで外した要望は作らず、元の経緯に残す。例: 「xxx・yyy・zzz をやる」にユーザーが「xxx と yyy だけ」と
答えたら、元を xxx に絞り、yyy だけを切り出す。

- 切り出した issue は、起票（「起票する」）に `--origin <元>` を付けて起こす（本文に「分割元: #<元>」の1行が入る）。ゲートはこの行で
  採否を元から受け継ぎ、入口で問わない。待つ意味は持たない。
- 完了の条件は、切り出す要望の分を元から移す（写さない。1つの条件は1つの issue にだけ置く）。どちらも、自分の条件が済めばゲートが閉じる。
- 種類・優先度・着手可能日時は、切り出した issue が自分で持つ（起票と同じ。「ラベルと種類と欄」）。

### 機能ごとに子に分ける（親子にする）

1つの要望の実現に要る機能の変更が大きく、Pull Request 1本に収まらなければ、機能ごとに子（sub-issue）へ分ける。親は要望のまま残り、
作業を持たない。

    node .claude/skills/file-issue/scripts/new-issue.mjs --parent <親> --title <題名> --body-file <本文> --size <規模> [--blocked-by <前の子>,...]

  （種類は親と同じになり、下の決まりに合わなければ作らない。）

- 親（要望）の約束は、ユーザーが確かめる要望の結果だけで、少なくとも1行持つ。機能の行（Claude が確かめる行）は、分けるときに親から子の本文へ移管する
  （文を変えずに移す。写さない）。子は自分の約束が全部果たされればゲートが閉じる。親の行を全部子へ移すと、親は約束0行になってその場で
  閉じ、開いた子が見送りで閉じるので、ユーザーが確かめる結果の行を持てない親（見せる結果の無い保守・不具合）は親子にせず切り出す。
  Pull Request を出さない作業（調べるだけ・本番で操作するだけ）は子にしない。
- 子が長く残る形（新しい表・保存の鍵・公開する API の形）を作るなら、子を起こす前に親で形を合意する（「issue の形」の「長く残る形は、作る前に合意する」）。
- 子は、優先度・着手可能日時・「急ぎ」・採否・保留を親から継ぐ（ゲートが親を読む）。子の欄へは入れない。子だけ別の値が要るなら、
  それは別の要望なので切り出す。種類は親と同じにする（対話作業かどうかを揃えるため）。規模は子の欄に入れる。
- 孫は作らない。子が大きすぎたら、同じ親の兄弟に分ける（子を1つに絞り、残りの約束の行を同じ親の新しい子の本文へ移管する）。
  孫を張ると、ゲートが張られた直後に外して知らせる。
- 親は、開いた子がある間は振り出されず、確かめも問われない（自分の約束が済めば、子に関係なく閉じる）。子が見送りで閉じると、ゲートが
  親で続けるかを一度だけ問う。親が開き直されない閉じ方で閉じると、ゲートが開いた子を見送りで閉じる。
- 親の作業ブランチに push 済みの変更があれば、その変更を含める最初の子へ渡す（親の枝に master を取り込み、
  `git push origin HEAD:refs/heads/orch/tasks-<子>` で置き、子の本文にコミットの ID を書く）。

### 開発機でしかできない作業

開発機でしかできない作業（`docs/conventions/flow.md`「担当」）は、種類を対話作業（`flow.config.json: dialogType`）にした issue を
起こし、元の issue の前提に張る（Pull Request を出さないので子にしない。担当へは振り出されない）。

    node .claude/skills/file-issue/scripts/new-issue.mjs --type 対話作業 --title <題名> --body-file <本文> --blocking <元>
