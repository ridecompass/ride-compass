# 既存のテストを見直す（消す・まとめる）

「3問」「1問目」等は、[testing.md](testing.md)「そのテストは要るか（3問を順に）」の問いを指す。

## 消す・まとめる前に、残す側が落ちるかを見る

**消す・まとめる前に、消すテストが落ちる実装の壊れ方を1つ書き、残す側がそれで落ちるかを見る。** どの経路で消す・
まとめるテストにも当てる（1問目の既に守られている・2問目の言えない・3問目の移した先が見ている・狭い方を消す・低い方に残す・
表の行へまとめる）。下の2・3は手で組み立てず、`scripts/break_tests.py`で流す（frontend も backend も同じ一覧で、`--ref`で前の版のテストも並べて回す。
一覧の形と使い方は道具の先頭）。

1. 消す・まとめるテスト1本ごとに、それが落ちる実装の壊れ方を1つ書く（比べ方を1つ変える・境界を1つずらす・値を定数へ変える）。
   書けないなら、そのテストは何も見ていない（1問目の恒真式）ので、確かめずに消す。
   宣言の書き写しは、宣言の値を変えることを壊れ方に数えず、書けないものとして確かめずに消す。並び・値が利用者に見える振る舞いを決める宣言は書き写しではない
   （「消すべきテストの型」）ので、並びを入れ替える・値を変える壊れ方を当てる。
   約束ごと消したテスト——見ていた約束が Pull Request の課題の「消した約束」か「変えた約束」の前の側に当たり、見ていた実装を
   同じ差分で消したもの——も、書けないものとして確かめずに消す。実装が後の版に残る
   （約束だけを変えた）テストはこれに当たらず、残った実装に壊れ方を書く。
   同じ側の行——通る書かれた比べ方のどれでも、残す側の入力と同じ側にある行（「同じ側の値を足さない」で消す・まとめる行と、
   3問目の「狭い方を消す」で消す行のうち入力が広い方と同じ側にあるもの）——には、書かれた比べ方の片側をまるごと変える壊れ方だけを
   当てる: 向きを反対にする・境界を1つずらす・比べ方を外して常に片側の結果にする・値を残す行の答えと違う定数へ変える。
   同じ側の中で答えを分ける壊れ方——別の比べ方へ置き換える（`in`を`==`へ・`Number.isFinite`を`Number.isNaN`へ）・
   書かれていない比べ方を足す（`if a:`を`if a and not b:`へ）・
   書かれた値の並びから1つ外す（`IN (…)`の値。並びの値ごとの行は宣言の書き写しで、値で結果が分かれるなら分類で同じ側ではない）・
   書かれていない既定値を足す（`?? 0`）・定数を残す行の答えに合わせる——は当てない。
2. 実装のその行を一時に変え、残す側（まとめた先の表・含むとした広い方・移した先・低い方）のテストのファイルだけを回して、
   次のどれかになることを見る。
   - (a) 残す側が落ちる。
   - (b) その壊れ方は作れない: 型・制約・宣言の検査（tsc・mypy・DB の制約・構造のテスト）が止める。止める検査を壊した版で
     回し、落ちることを見る（テストのファイルなら残す側に並べる。tsc・mypy は壊した版で打ち、3 と同じく戻す）。
     `break_tests.py` が「テストの前に止まった（(b)）」と止まり方の1行（例外の行）を出した件は、その行を 4 の出力として書く。
     型の計算を自前で書いたもの（パスの文字列から引数の型を導く等）は、その計算を崩しても tsc が通るので (b) に数えない。
   - (c) 前の版の消すテストも、その壊れ方で落ちない（`--ref`で並べて回す）: 消すテストは何も見ていなかった。

   どれにもならなければ、残す側を直す（表の補助が見る値を足す・行を足す）か、消さずに残す。
3. 変えた行を編集で戻し、`git diff --exit-code -- <実装のファイル>` で戻ったことを見てから次へ進む。
4. 約束が残るのに消した・まとめたテストは、Pull Request の本文の検証に1件ずつ、守っていた壊れ方と結果（(a) 落ちたテストの名前・
   (b) 止めた検査とその出力・(c) 前の版でも落ちなかったこと・壊れ方が書けない理由（恒真式・宣言の書き写し））を書く。同じ側の行は、
   どの書かれた比べ方（実装のファイルとその比べ方）の同じ側かも書く。約束ごと消したテストと、題名や用語を変えただけのテストは書かない
   （消した約束は課題の約束の差分に書く）。

**消す・まとめる・題名を変えるテストを名指す設計書の行は、同じ差分で直す。** 手を入れたテストの
ファイル名を `docs/` で grep し（例: `grep -rn 'legends.test' docs/modules`）、そのテストが確かめる・固定すると書いた行があれば、
保証の今の置き場（残す側のテストとその題名・型・源泉の宣言）に合わせて書き直す。

**「対象へ届いているか」は測れる。** `pytest --cov=app --cov-context=test`でテスト単位の
文脈を取り、対象モジュールの行を1つも実行していないテストを機械的に出す。ただし
**定数・型宣言を見るテストは対象の行を実行しない**（SQL文字列の定数・規則表・Pydanticの
`Field`制約・`Protocol`の宣言はimport時に評価される）ので、この信号だけでは判定しない。
出たものを3問へ通す。

## テストを変異テストで見直す（効き・重なり・隔離・書き方）

見直しの物差しは、どの層も3問と効き（守るべき壊れが起きたら本当に落ちるか）。3問は1本ずつ読んで判じる。単体テスト（backend・
frontend）では、変異テスト（実装を1か所ずつ書き換え、どのテストが落ちるかを記録する）で、4つの観点を全部のテストへ機械で当てられる。
e2e には変異テストを使わない（下の「e2e を3問で見直す」）。3つの層を見直す1回の回し方は [test-review/SKILL.md](../skills/test-review/SKILL.md)、
層ごとの測りの起こし方と台本の口は [run-checks/SKILL.md](../skills/run-checks/SKILL.md)「変異テストでテストの効きを測る」。
測りの結果はどの層も同じ表の形にし、同じ台本（`backend/scripts/mutation/review.py`）が候補を出すので、ここの決まりは層に依らない。
層ごとに違うのは、表を作る所（道具と、書き換えを作らない所の設定）だけ。
**消す側だけを見ない**: 足す（効き）・直す（隔離・書き方）・消す（重なり）を同じ測りから出す。
**候補は消す・足す一覧ではない。** 変異テストは、壊れが利用者に届くか（2問目）を見ない。候補は1件ずつ、落ちると利用者に何が
壊れるかを書いてから、消す・足す・直すをユーザーが決める。

この測りが見ないもの: 書き換えを作らない所（どのテストも見ない書き換えが生き残りに混ざる所。どこかは層ごとの設定が持つ。
backend は `backend/scripts/mutation/setup.cfg`、frontend は `frontend/scripts/mutation/stryker.config.mjs`）・backend では関数の外
（モジュールの直下の表・定数・既定値）・部分どうしのつなぎの食い違い・本番のデータで初めて出る問題・実画面でしか出ないもの・
テストの名前と例が振る舞いを言葉で説明する役。そこを確かめるテストは、変異を見つけないように見えても要らないとは言えない。

基準（変異を入れない版で、同じテストの組み合わせを同じ並びで2回回す）を回す層では、「見つけた」は、2回とも通ったテストが変異で
落ちたものだけ。基準で落ちるテストは、テストどうしの依存や揺れで落ちていて、壊れ方を見つけたとは言えない（それは隔離で直す）。
基準を回さない層の表は、隔離の候補を出さない。

### 効き: 生き残りにテストを足す

どのテストも見つけない変異（生き残り）に2問目（落ちるとき、モジュールの外の何が壊れるか言えるか）を当て、言えるならその壊れ方で
落ちるテストを足す。言えない（振る舞いが変わらない・丸めの桁のように外へ効かない）なら足さない。

- 全部を回す測りでは、生き残りが効きの候補に出る。言えたものを足す候補にしてユーザーに問う。
- Pull Request ごとの測りがある層（`.github/workflows/mutation-pr.yml`）では、変えた関数の変異と基準だけが回り、生き残りが変えた行への
  注記に出る。言えないものは、本文の検証にその理由を1行で書く。読み方と書き方は [task-work/SKILL.md](../skills/task-work/SKILL.md)「実装担当」の5。

### 重なり: ほかと重なったテストを消す

3問目（ほかに同じことを見ているものがあるか）を、全部を回す測りの記録で当てる。候補ごとに、落ちると利用者に何が壊れるかと、
それを残すテストが守るかを書いてから、消すかをユーザーが決める。前の測りでも候補で中身が同じテスト関数には印が付く（前の測りの
候補は見直しの成果物が持ち、次の測りの見直しが比べる）。印は判断の材料で、印の無い候補も同じに問う。変異を回し終えていない測りは、
候補が欠けるので問わず、比べにも次の前回にも使わない。

候補は、次の全部を満たすテスト関数（パラメータの組の数え方は `backend/scripts/mutation/review.py` の先頭）。

1. **見つける壊れ方が、全部ほかの残すテストでも見つかる。**
2. **どれを残すかは3問目の向きで決める。**
   - 別の高さで同じ壊れ方を見ているなら、低い方に残す。テストの高さは、そのテストが通る変異のファイルの層（表の層の並び。
     表を作る所が、backend は `backend/.importlinter`、frontend は `frontend/eslint.config.mjs: LAYERS` から書く）のうち一番上。
     ただし、ほとんど全部のテストが通る足場の変異（本数のしきい値は `backend/scripts/mutation/review.py: SCAFFOLD_TESTS`）と、
     読み込みのときに呼ばれる変異は高さに数えない。上の層のテストは、同じ高さ以下の残すテストで見つかる壊れ方しか見つけていなければ候補。
   - 同じ高さの中では、広い方（ほかで見つからない壊れ方を多く見つける方）を残し、狭い方を候補にする。
   - backend の API の経路（`app/api/routers` の関数）ごとに、それを通るテストを1本は残す（3問目の「経路ごとに受け渡しを1本は残す」）。
3. **判断できないものは候補にしない。**
   - 読み込みのときに呼ばれる関数（モジュールの直下・クラスの本体・既定値・デコレータで呼ばれる関数）の変異を見つけるテスト。
     変異テストの記録は、その呼び出しをその時に走っていたテスト1本にしか結ばず、ほかのどのテストが見つけるかが当てにならない。
   - 変異を1つも見つけないテストと、上の「この測りが見ないもの」だけを確かめるテスト（「測れていない」で、要らないとは言えない。
     書き方で見る）。
   - 通る変異が足場と読み込みのときに呼ばれる変異だけで、高さが決まらないテスト。
   - 隔離が直っていないテスト（下の隔離で、汚す側か汚される側に当たったもの）。
4. **消したあとに確かめる。** 消すテスト1本ごとに、それが見つけていた壊れ方のうち同じ高さ以下の残すテストが見つけるものを1つ選び、
   消したあとの版でその変異を回して、残すテストが落ちることを見る（層ごとの回し方は test-review/SKILL.md の5）。テスト全体が通ることは
   Pull Request の CI が見る。落ちたら、消したテストを戻して隠さず、隔離で汚した側を直す（直すまで、そのテストは消さない）。
   Pull Request の本文の表（上の「消す・まとめる前に…」の4）は、この壊れ方と結果で書く。

### 隔離: 並びで落ちるテストは、汚した側を探して直す

並びを変えた回にだけ落ちる（汚される側）なら、その前に同じプロセスで走ったテストのどれか（汚す側）が状態を残している。
**落ちたテストを消したり、汚す側を戻したりして隠さない。** 汚す側を探して、状態を残さない形（フィクスチャの片付け・
プロセスに残る記録を使わない）に直す。直すまで、汚す側と汚される側のどちらも重なりの候補にしない。
backend の探し方は [run-checks/SKILL.md](../skills/run-checks/SKILL.md)「実行順をばらす（pytest-randomly）」。

### 書き方: 測りから出た形を、型として足す

全部を回す測りから、次のテストを書き方の見直しの候補に出し、1本ずつ3問へ通す（backend は、既製の書き方の検出器に pytest に
使えるものが無い（PyNose は unittest と PyCharm だけ、pytest-smell は作りかけの研究用）ので、測りから出す）。

- **通るのに何も見つけない**: 変異を通るのに、1つも見つけない。確かめが弱い（値を見ずに型や件数だけを見る）か、
  1問目・2問目で要らないものが多い。
- **広くしか落ちない**: 見つけた変異が全部、多くのテストが一緒に落ちる書き換え（どのテストでも落ちる壊れ方。本数のしきい値は
  `backend/scripts/mutation/review.py: BROAD_TESTS`）だけ。そのテストだけが確かめていることが、変異で見えていない。値を見る確かめが
  弱いか、3問目で広い方に含まれる。

見直して出た形のうち機械で見分けられるものは、「消すべきテストの型」へ行を足し、その層の構造の検査（`backend/tests/structure`・
`frontend/src/structure`）に足す。

## e2e を3問で見直す

e2e は、実画面でしか出ず機械で判定できるものを見る（[testing-e2e.md](testing-e2e.md)「パターン4」）。その壊れは実装の書き換えでは
入らないので、変異テストを使わず、`frontend/e2e/` のテストを1本ずつ読んで3問を当てる。e2e の効きを確かめる道具は作らない。

1. **1問目**: 全状態の走査（`frontend/e2e/all-states.spec.ts` が当てる `frontend/e2e/scans.ts` の検査）が、同じ観点を同じ画面の
   状態で既に見ていないか。見ていれば消す候補。
2. **2問目**: 冒頭のコメントで、パターン4のどの観点を見ているか言えるか。DOM の状態・ロジックだけを見ているなら vitest へ移す
   候補、何も言えなければ消す候補。観点は言えるのにコメントが無い・食い違うなら、コメントを直す候補。
3. **3問目**: 同じ観点・同じ画面の状態を、別の e2e のテストが見ていないか。見ていれば狭い方を消す候補。

候補は単体テストと同じく、1件ずつ落ちると利用者に何が壊れるかを書いてから、ユーザーが決める。消す・まとめるときは上の
「消す・まとめる前に、残す側が落ちるかを見る」を当てる（`scripts/break_tests.py` は e2e を回さないので、2・3 は実装の行を一時に変え、
残す側の spec だけを Playwright で回して見る）。

## 消すべきテストの型

| 型 | 見分け方 |
|---|---|
| **正しく直すと落ちるテスト** | 実行せずに、SQL文字列やパスへ特定の名前が含まれることをアサートする |
| **空振りの検知器** | 「Xが作る形を検証する」と書きながらXを呼ばず、期待値を手で書いている |
| **宣言の書き写し** | 定数・モデルの既定値・レジストリの中身をテスト側へ再掲して突き合わせる。ただし宣言の並び・値が利用者に見える振る舞い（地図に描く順・既定で選ばれる項目）を決めているなら、書き写しではなく振る舞いの確かめである。宣言に対して書いてよいのは、型・導出で保証できないときの、**導出した母集団すべてに対する不変条件**（要素が1つ増えたときに発火するもの。testing.md「そのテストは要るか（3問を順に）」の「本番のデータそのものに対する不変条件」）だけで、手で名指しした数件に対する検査は書かない（設計原則 構造仕様12） |
| **恒真式** | `set(versions) == set(TILE_SHAPES)`（同じ内包表記の結果を同じ定数と比べる） |
| **効いていない除外リスト** | ガードに付けた除外の一覧（効いているかを測っていない一覧には、存在しないファイル名や、先行条件で既に弾かれるものが残る） |
| **消したものを見張るアサーション** | `assert not cleared`のように、呼ばれないことを確かめる |
| **等価テスト** | 新旧2実装の出力一致。代わりに、**入力に対するあるべき値**を書いた期待値テストを**生きている1本の実装へ当てる**。移行が終わったら等価テストは消す |
| **カバレッジの水増し** | 「落ちるとき何が壊れるか」に答えられない。`MIN <= MAX`・`isinstance(x, int)`・定数への等値 |
| **実装の規則の再実装** | 実装が「名称に『特別警報』を含むか」で決めているのを、テストも同じ規則で期待値を作る |
| **型が保証していることの検査** | 戻り値が3値の`Literal`なのに「3値のいずれかへ落ちる」を確かめる |
| **本番に生えたテスト専用の口の検査** | テスト専用の初期化関数（`reset_*_for_testing()`の類）が状態を空にすることを確かめる |
| **宣言から作った足場へ宣言を当てる** | 宣言された全クラスについて`em.lc_{key}`が読めることを、`lc_{key}`という列を自分で用意して確かめる。宣言された語彙の全件が`= ANY(:語彙)`で真になることを確かめる。**振る舞いがidごとに違わないなら、性質ごとに1件で足りる**。「宣言した列・値が実在するか」は実テーブル・実カタログへ通して確かめる |
| **テストのフィクスチャに対する不変条件** | `AXIS_DEFINITIONS`の全軸が排他チェックを通ることを確かめる（テスト中の中身は注入したフィクスチャ）。**その宣言がテスト中に差し替わるなら、全件の不変条件は書かない**。足場そのものを対象と名乗る足場のテスト（testing-scaffold.md パターン5）はこれに当たらない |

## 黙って縮退する分岐は、取り除いて実験する

**「この分岐は要るか」をコードを読んで決めない。** 母集団を機械で導き、1件ずつ取り除いてテストを流す。

母集団（AST）: **例外を送出せずに縮退した結果を返す分岐**——空を返す`return`・`.get(`・
`x or y`・`except: pass`。変異は縮退の道を外す（`x or y`→`x`、`d.get(k)`→`d[k]`、
`except: pass`→`except: raise`、空の`return`→`raise`）。

- **落ちる** → その縮退はテストが見ている。仕分け終わり
- **通る** → 誰も見ていない。**要確認**へ送る

**コメントの語（「通常は到達しない」「念のため」「防御的」）でgrepしない。**

**「テストが見ていない」は「消すべき」を意味しない。** 消すか要件かは別の事実で判定する。**要確認を群にまとめるときは、その縮退が起きる実データ
上の条件を1つ挙げてからまとめる**——挙げられないものは別の群にする。

### 要確認の出し方

**欠陥と判定する前に、対比先（宣言の隣のコメント・docstringが対で読めと指す関数）が本当に何を言っているかを読む。**

問いの形と届け方は[ask/SKILL.md](../skills/ask/SKILL.md)「問い」が正本。テストの欠陥の要確認で判断材料に足すのは次の2つだけ。

**設計書・コード・テストが、それぞれ何を主張しているか。** 利用者への約束と場面の次に、3行の表で、
**同じ粒度・実装の語を使わずに**（「コードはこう実装されている」ではなく「コードはこう主張している」）。

**選択肢は2つ。消すか、残すか。** 添えるのは**消したとき外で何が起きるか**と**その道を通る
呼び出し元の件数**だけ。

## テストと実装のずれを疑う印

- **ファイル名が指すモジュールを検証していない。**
- **テストにだけ残った語彙。** 実装から消えた機構の名前がフィクスチャ名・テスト名に残る。
  実装側と突き合わせれば機械的に出せる。
- **テストのために本番コードへ生えた宣言。** 消費者が`backend/tests/`だけの公開名のうち、
  testing.md「確かめる高さ」の (a)〜(c) に当たらないもの。
